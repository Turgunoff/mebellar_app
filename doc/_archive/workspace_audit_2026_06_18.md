### [woody_backend] BE-01 — Eskiz SMS failure wedges OTP login: code committed but EskizError surfaces as raw 500 and cooldown already claimed
- **✅ RESOLVED (2026-06-18):** `EskizClient` now wraps `httpx` transport errors as `EskizError` (`_post_sms`/`_login`); `OtpService.request_otp` keeps the atomic SEC-02 claim but rolls it back (deletes the `otp_codes` row) and raises the new typed `SmsDispatchFailed(AuthError)` when `send_sms` fails; the router maps it to **502 `sms_unavailable`**. A failed dispatch no longer consumes the cooldown, and an Eskiz error/timeout returns a typed 502 instead of a raw 500. The catch stays scoped to `EskizError` so genuine non-domain faults still 500 (regression-tested). Tests added in `tests/unit/test_otp_service.py`, `tests/test_auth_endpoints.py`, `tests/unit/test_eskiz.py`; full suite green.
- **Severity (orig→adj):** High → Medium  | **Category:** bug  | **Confidence:** high
- **Location:** `app/services/otp.py:161-179 (request_otp) + app/api/v1/auth.py:43-77 (_translate)`
- **Problem:** request_otp() first atomically claims the cooldown window and persists the OTP row via claim_request() (committed in its own connection), THEN does `await self._eskiz.send_sms(...)`. If Eskiz times out or returns a non-recoverable error, send_sms raises EskizError. EskizError is NOT a subclass of AuthError, so the router's `except AuthError` does not catch it — the caller gets an unhandled 500 instead of a typed error. Worse, the OTP row's last_request_at was already set to now, so the OTP_REQUEST_COOLDOWN_SECONDS (60s) cooldown is now active even though no SMS was ever delivered: the user cannot re-request a code for a full cooldown, and never received one. Any transient Eskiz hiccup therefore locks a user out of login for the cooldown window. The Eskiz client also awaits up to ~10s (×2 on a 401 token-refresh retry ≈ 20-30s) holding the request, compounding the impact during an Eskiz outage.
- **Fix:** Translate EskizError to a clean 502/503 in the router so clients can retry, AND roll back the cooldown claim on a failed dispatch (e.g. delete/reset the otp_codes row in a try/except around send_sms) so a failed SMS does not consume the user's cooldown. Consider sending the SMS before committing the claim, or deleting the row on EskizError so an immediate retry is allowed.
- **Verify note:** Real and confirmed. Two distinct defects: (a) EskizError/timeout surfaces as a raw 500 instead of a typed error (router can't catch it); (b) cooldown is committed before the SMS send, so a failed send locks the user out for the cooldown window with no code delivered. Both are correct as described. Downgraded High→Medium: impact is gated on a third-party (Eskiz) outage/hiccup, is self-healing after the cooldown (default 60s), and does not corrupt data or breach security. Suggested fix: move claim_request AFTER a successful send (or delete/reset the row on send failure), and wrap send_sms so EskizError/TimeoutException map to a typed AuthError (e.g. a 502/503 'sms_unavailable') without claiming the cooldown.

### [woody_backend] BE-02 — Admin scope gating fails OPEN for any /admin/ path segment not listed in _PATH_SCOPE
- **✅ RESOLVED (2026-06-18):** `scope_for_admin_path()` now fails **closed**. Unmapped `/admin/` segments return the new `UNKNOWN_SCOPE` sentinel instead of `None`, and `has_permission()` denies `UNKNOWN_SCOPE` to scoped moderators (super_admin and full managers still pass). The intentionally-ungated segments are an **explicit allowlist** (`_UNGATED_ADMIN_SEGMENTS = {dashboard, storage}`), so a new admin router with a forgotten `_PATH_SCOPE` entry is denied by default rather than silently leaked. A regression test (`tests/unit/test_rbac.py::TestAdminRouterSegmentCoverage`) asserts every registered `/admin/` router segment is mapped in `_PATH_SCOPE` or whitelisted, and `TestAdminScopeFailsClosed` locks the fail-closed behaviour. `app/security/rbac.py`.
- **Severity (orig→adj):** Medium → Low  | **Category:** security  | **Confidence:** high
- **Location:** `app/security/rbac.py:130-160 (scope_for_admin_path + has_permission)`
- **Problem:** scope_for_admin_path() returns None for any /admin/<segment> whose first segment is absent from the _PATH_SCOPE dict. In has_permission(), `scope is None` is treated as an intentionally ungated path and a SCOPED moderator passes (`if scope is None: return True  # ungated path`). The mechanism cannot distinguish 'deliberately ungated' (dashboard, storage) from 'developer forgot to map a new admin router'. Consequence: any future admin router added under a new /admin/<newsegment> prefix WITHOUT a corresponding _PATH_SCOPE entry becomes silently accessible to every scoped moderator regardless of their granted scopes — a latent privilege-escalation. All current admin routers do use /admin/<segment> prefixes (verified in products.py:25, orders.py:12, settings.py:17, managers.py:26, etc.), so the dependency is real, and the only safeguard is developer discipline + a cross-repo mirror in lib/auth/roles.ts.
- **Fix:** Fail closed for unmapped admin paths: maintain an explicit allowlist of intentionally ungated segments (dashboard, storage) and have scope_for_admin_path return a sentinel like 'UNKNOWN' (not None) for anything else, which has_permission denies to scoped moderators. Add a test asserting every registered /admin/ router segment is present in _PATH_SCOPE.
- **Verify note:** Real fail-open design weakness, confirmed in code. Downgraded Medium→Low: the impact is LATENT, not an active vuln. Every one of the 18 current admin segments is either explicitly mapped in _PATH_SCOPE or intentionally ungated (dashboard/storage, by documented design). There is no current router that leaks a scope a moderator shouldn't have. The risk only materializes the day someone adds a new /admin/<segment> router and forgets the _PATH_SCOPE entry — a regression-prone footgun rather than a present escalation. Robustness fix worth doing (fail-closed default: unknown /admin/ segment should map to an owner-only/unknown scope and 403 scoped moderators, with dashboard/storage explicitly whitelisted), but it is not exploitable as-shipped.

### [woody_backend] BE-03 — AR webhook shared-secret compared with non-constant-time `!=`
- **✅ RESOLVED (2026-06-18):** The secret check now uses `hmac.compare_digest(x_ar_webhook_secret or "", expected)` — constant-time, matching the OTP path's idiom. A missing header (None) is coerced to `""` so presence isn't leaked through a length-based branch. Existing `test_ar_webhook_rejects_bad_secret` still passes (wrong/missing → 401, correct → 200). `app/api/v1/ar_webhook.py`.
- **Severity (orig→adj):** Medium → Low  | **Category:** security  | **Confidence:** high
- **Location:** `app/api/v1/ar_webhook.py:36-41`
- **Problem:** The /internal/ar-webhook endpoint is explicitly the one write path guarded by a shared secret rather than a JWT (it can flip a product into pending_review and attach an arbitrary model_url). The secret check uses `if expected and x_ar_webhook_secret != expected`, a plain string inequality that short-circuits on the first differing byte and is therefore vulnerable to a timing side-channel for secret recovery. The OTP path already uses hmac.compare_digest for exactly this reason (otp.py:199), so the codebase knows the pattern.
- **Fix:** Compare with hmac.compare_digest(x_ar_webhook_secret or '', expected) so the comparison is constant-time. Also consider rejecting when the secret is unset in non-dev environments rather than leaving the endpoint open.
- **Verify note:** Real but over-rated as Medium. The `!=` is genuinely not constant-time and deviates from the codebase's own hmac.compare_digest idiom on a security-boundary write path, so the fix is warranted and trivial. However remote timing-side-channel recovery of a high-entropy shared secret over HTTP/network is impractical (CPython str comparison length-checks first then memcmp; network jitter swamps per-byte timing). Note also `if expected and ...` means an unset/empty AR_WEBHOOK_SECRET leaves the endpoint fully open (intentional per docstring for dev/CI) — a bigger real risk if the secret isn't configured in prod, but that's a config/deployment concern, not this finding. Fix: replace with hmac.compare_digest(x_ar_webhook_secret or "", expected).

### [woody_backend] BE-04 — Meshy .glb download is unbounded in memory and content-type/size unvalidated before re-hosting to R2
- **✅ RESOLVED (2026-06-18):** `download_glb()` now **streams** via `httpx.stream(...)` with a 75 MB ceiling (`_MAX_GLB_BYTES`): an over-cap `Content-Length` is rejected before the body is read, a per-chunk running total catches a missing/lying length mid-stream, and a non-binary `Content-Type` (HTML/JSON/XML/text — a redirected/poisoned URL) is refused rather than re-hosted. The AR worker adds a non-empty-body guard before `put_object()` so a 0-byte download is never re-hosted as an orphan (it raises into the bounded-retry path). Tests in `tests/unit/test_meshy_client.py` (oversized header, mid-stream cap, non-model content-type) and `tests/unit/test_ar_pipeline.py::test_empty_glb_download_does_not_attach`. `app/clients/meshy.py` + `app/services/ar_pipeline.py`.
- **Severity (orig→adj):** Medium → Low  | **Category:** edge-case  | **Confidence:** high
- **Location:** `app/clients/meshy.py:148-154 (download_glb) + app/services/ar_pipeline.py:225-232`
- **Problem:** download_glb() returns response.content with no Content-Length cap and no streaming — the entire model is buffered into a single bytes object in the event-loop process, then handed to storage.put_object(). The glb_url comes from Meshy's task payload (model_urls.glb); the worker trusts whatever URL/size that response carries. A pathologically large or wrong-type response (Meshy bug, or a redirected/poisoned signed URL) would balloon worker memory and re-host arbitrary bytes under the public product-ar-models bucket with a hardcoded model/gltf-binary content-type. Lower likelihood because Meshy is a trusted provider behind an API key, but there is no defensive bound on a fully external, variable-size download running on a background loop.
- **Fix:** Stream the download and enforce a max-bytes ceiling (abort + MeshyError past, say, 50-100 MB), and sanity-check the response Content-Type/Length before put_object. The httpx client already has a 120s timeout; add a size guard to match.
- **Verify note:** Real but conditional hardening gap. The glb_url is sourced from Meshy's API-key-authenticated task payload, not from untrusted user input, so exploitation requires a Meshy provider bug or a poisoned/redirected signed URL. The finding itself acknowledges the low likelihood ("trusted provider behind an API key"). Code does NOT guard against it (no size cap, no content-type sniff, no streaming), so the defensive-bound concern stands — but impact is downgraded from Medium to Low given the trusted source and the existing 120s timeout that bounds download duration. A simple max-bytes check on response.headers Content-Length plus a streamed download with a running-total guard would close it.

### [mebellar_app] OTP-01 — Android SMS autofill never re-arms on OTP resend
- **✅ RESOLVED (2026-06-18):** `_listenForSmsCode()` no longer early-returns on an already-active listener. It now tears down any prior `smart_auth` listener (`removeSmsRetrieverApiListener()` + `removeUserConsentApiListener()`) before re-arming, and a monotonic `_smsListenGeneration` token invalidates a superseded in-flight listen so a stale result/teardown can't clobber the fresh one. A resend therefore re-arms zero-tap autofill. The `!Platform.isAndroid` early-return is preserved (off-Android stays a no-op). `lib/auth/auth_sheet_controller.dart`.
- **Severity (orig→adj):** High → Medium  | **Category:** bug  | **Confidence:** high
- **Location:** `lib/auth/auth_sheet_controller.dart:247-266 (_listenForSmsCode) + 100 (sendOtp)`
- **Problem:** _listenForSmsCode() early-returns when `_smsListenerActive` is true. The flag is only cleared in the `finally` AFTER `getSmsWithRetrieverApi()` / `getSmsWithUserConsentApi()` completes — and those futures stay pending until an SMS actually arrives (Retriever) or the user dismisses the consent dialog. When the first code never arrives and the user taps 'Kodni qayta yuborish', sendOtp() calls unawaited(_listenForSmsCode()) again, but the still-active first listener makes it a no-op. The resent SMS therefore does NOT autofill — the most common real-world OTP path (first SMS delayed by the Eskiz/operator queue, user hits resend) silently loses zero-tap autofill and forces manual entry. The Retriever API also has its own ~5 min server timeout, so the listener can be stuck for minutes.
- **Fix:** Tear down the previous listener before re-arming on resend: in sendOtp() (or at the top of _listenForSmsCode) call SmartAuth.instance.removeSmsRetrieverApiListener()/removeUserConsentApiListener(), reset `_smsListenerActive=false`, then start a fresh listen. Alternatively drop the guard and let each request start its own listener after cancelling the prior one.
- **Verify note:** Real and unguarded. Severity tempered to Medium (from High): in the Retriever path the still-active first BroadcastReceiver matches any SMS containing the app-signature hash, so the *resent* SMS can still be caught by the original pending listener and autofill anyway — the no-op second call does not always defeat autofill. The clear loss is in the User Consent path (debug/sideloaded), where the first attempt's consent flow is bound to the first SMS token and the resend gets no fresh consent dialog. Also degrades zero-tap reliability generally. Fix is straightforward: drop the `_smsListenerActive` early-return on resend, or tear down + re-arm (removeSmsRetrieverApiListener/removeUserConsentApiListener then re-call) inside _listenForSmsCode when already active. Not a crash or data issue, hence Medium.

### [mebellar_app] OTP-02 — Pin field auto-submit fires via an uncancelled delayed callback, can re-submit after error-clear
- **✅ RESOLVED (2026-06-18):** The 120ms auto-submit and 500ms error-clear `Future.delayed` calls are now cancellable `Timer`s, both cancelled in `dispose()`; the submit timer is also cancelled at the top of every `_handle`. A `_lastSubmittedValue` guard fires `onCompleted` exactly once per unique completed code (reset when the error-clear wipes the field, so a legitimate re-submit still works). Widget tests in `test/auth/sheets/otp_step_test.dart` cover the single-fire guard and the backspace-then-retype race. `lib/auth/sheets/otp_step.dart`.
- **Severity (orig→adj):** Medium → Low  | **Category:** edge-case  | **Confidence:** high
- **Location:** `lib/auth/sheets/otp_step.dart:175-183 (_handle) and 147-164 (didUpdateWidget)`
- **Problem:** _handle() schedules `Future.delayed(120ms, onCompleted)` every time the controller reaches full length, with no handle to cancel it. On a wrong code, didUpdateWidget schedules a separate 500ms delayed controller.clear()+refocus. Sequence: full code typed → 120ms submit scheduled; server rejects → hasError flips → 500ms clear scheduled. The two timers and the autofill path (otpCtrl.text=code in the controller, which also trips _handle) can interleave so onCompleted() fires again on a partially-cleared field. verifyOtp() guards with `code.length < 4` and `_isLoading`, so the worst case is a redundant verify attempt / a wasted OTP attempt against the backend rate limiter rather than a crash — but it is a real double-submit window, and autofill setting the full code triggers the same 120ms path the moment digits land.
- **Fix:** Store the Timer from _handle and cancel it in dispose and at the start of each _handle; guard onCompleted so it only fires once per completed value (track the last-submitted value). Don't rely solely on the cubit's _isLoading flag for de-dup.
- **Verify note:** Real but minor. Uncancelled Future.delayed timers exist as described; concurrent double-submit to backend is impossible due to the synchronous _isLoading guard. Worst case is one wasted OTP attempt in a rare timing window, not a crash or a true concurrent double-submit. Cheap fix: store the 120ms/500ms timers as cancellable Timer handles and cancel in dispose / on error-clear.

### [mebellar_app] TOK-01 — TokenStore.read() hydration is not atomic under concurrent first callers
- **✅ RESOLVED (2026-06-18):** Hydration is now single-flight: `read()` returns the cache when `_hydrated`, else awaits a memoised `_hydration ??= _hydrate()` so a cold-start burst shares one storage round-trip. `_hydrate()` also bails to an authoritative `write()`/`clear()` value that landed mid-flight rather than clobbering it with stale reads. Tests in `test/core/network/token_store_test.dart` (5 concurrent reads → 1 round-trip; write-during-hydration not clobbered). `lib/core/network/token_store.dart`.
- **Severity (orig→adj):** Low → Low  | **Category:** edge-case  | **Confidence:** high
- **Location:** `lib/core/network/token_store.dart:47-66`
- **Problem:** read() checks `if (_hydrated) return _cached` then performs three awaited secure-storage reads before setting `_hydrated = true`. At cold start a burst of authenticated requests (the interceptor reads tokens per request) can enter read() concurrently before _hydrated flips, so each performs its own 3 Keychain/EncryptedSharedPreferences reads. Functionally correct (idempotent reads) but wasteful, and on Android EncryptedSharedPreferences concurrent reads have historically thrown on some devices. The single-flight pattern used for refresh (_refreshFlight) is exactly what's missing here.
- **Fix:** Memoise an in-flight hydration Future: `Future<TokenPair?>? _hydration; read() => _hydrated ? _cached : (_hydration ??= _hydrate());` so concurrent callers await one storage round-trip.
- **Verify note:** Confirmed as a real but trivial micro-inefficiency. Severity stays Low (arguably negligible/won't-fix). The single-flight parity argument with _refreshFlight overstates the case: refresh needs single-flight because it rotates the token (non-idempotent); read() is idempotent so the cost is only a few duplicate storage reads at cold start, not a correctness or security risk. The Android "concurrent reads throw" justification is speculative and historically applied to writes, not reads. A one-line fix (wrap hydration in a cached Future) is cheap but low-value.

### [mebellar_app] CART-01 — Guest cart merge replays items sequentially with awaited network calls and swallows all failures
- **✅ RESOLVED (2026-06-18):** `_mergeGuestCart` now replays lines in parallel via `Future.wait`, classifies each outcome (merged / permanent-drop / transient-keep — permanent = a 4xx other than 401/429), removes from the local Hive cart only the merged and permanently-dropped lines (transient failures stay to retry), and emits a `CartMergeResult{merged, dropped}` on the new `mergeEvents` stream so the UI can surface lost items. Regression test asserts a transient line is kept, a 404 line dropped, and both counts reported. `lib/shared/repositories/hybrid_cart_repository.dart`.
- **Severity (orig→adj):** Low → Low  | **Category:** tech-debt  | **Confidence:** high
- **Location:** `lib/shared/repositories/hybrid_cart_repository.dart:64-79 (_mergeGuestCart)`
- **Problem:** On login _mergeGuestCart awaits remote.addProduct() for each guest line one-by-one inside a for loop, catching and silently discarding every error. For a large guest cart on a slow connection this serialises N round-trips before the local cart is cleared and the server snapshot is fetched, blocking the post-login experience. Worse, because failures are swallowed per-item with no surfaced result, an item that fails to merge (out of stock, removed) just disappears from the user's cart with no feedback — the guest loses items they intended to buy. - **Verify note:** Confirmed as written; severity stays Low. The serialisation/blocking angle is overstated (background, small carts); the silent-loss-on-transient-failure angle is the legitimate core. ### [woody_admin] AUTH-01 — Token refresh writes cookies during Server Component render → silent logout after access-token TTL

- **Problem:** The CSP is shipped as Content-Security-Policy-Report-Only and (per CLAUDE.md gotchas) there is no report-uri/report-to directive and no report collector. In Report-Only mode with no reporting sink, the policy does nothing at all: it neither blocks attacks nor records violations, so the 'flip to enforce once the report log is clean' plan has no log to clean. ## Strengths — woody_backend
- Authentication is exceptionally well-hardened against the exact concurrency bugs in scope. OTP request cooldown is claimed via a single conditional upsert (repositories.py:311 claim_request, ON CONFLICT ... WHERE last_request_at < now - cooldown), OTP verify counts the attempt atomically before comparing (bump_and_get, otp.py:224), and refresh-token rotation uses a conditional claim_revoke so only one of two racing refreshes wins and reuse scorches the whole chain (otp.py:268-326). These directly close the documented SEC-01/02/04 TOCTOUs.
- The wallet/commission money path is the strongest part of the codebase: every balance mutation funnels through apply_wallet_delta() under SELECT ... FOR UPDATE inside the caller's transaction, with an immutable ledger row carrying balance_after; commission is made idempotent under order-status flapping via the partial unique index wallet_tx_commission_once_idx + ON CONFLICT DO NOTHING (wallet.py:104-183, 249-282); top-up approval is locked FOR UPDATE with a status guard so double-approve is a no-op (wallet.py:422-454).
- Order creation correctly enforces one-shop-per-order server-side (customer_repos.py:637-643, MultiShopCartNotSupported) to close the multi-shop IDOR/commission-loss cluster, re-derives ALL pricing/fees server-side from the products table (never trusting client prices, _compute_invoice + _PRICING_SQL which filters to approved products of active shops), and wraps the orders+order_items fan-out in a single transaction with the read-back outside it.
- Storage IDOR is thoroughly addressed: presigned-URL issuance binds the object key to the caller (_assert_path_owned, user_storage.py:108-172) for user-prefixed, shop-scoped, and product-image keys, and chat-attachment keys are server-issued (_server_chat_key) so a client can't target/overwrite an existing object.
- Blocking I/O is correctly kept off the event loop: the synchronous firebase-admin SDK is offloaded via asyncio.to_thread with 500-token multicast chunking and dead-token pruning (fcm.py:119-193), and AUTO_MIGRATE runs alembic in a thread. External clients (Eskiz, Meshy, Azure) all use async httpx.
- Background workers (NotificationDispatcher, ArPipelineWorker, TariffExpirySweeper, WalletDebtSweeper) are defensively built: per-item try/except so one poisoned row can't wedge the loop, claim-before-send watermarking for multi-worker dispatch idempotency (notifications.py:317), bounded retries with in-memory attempt counters + stale backstops (ar_pipeline.py), and AI/AR endpoints degrade gracefully (always-200 ai-suggest, 503 when AR disabled).
- Indexing is comprehensive for the hot filter/FK columns: cart_items/favorites/orders by user_id, order_items by order_id, products by shop_id/seller_id/status/category, reviews by product/shop, chat_messages by (chat_id, created_at), wallet_transactions by seller/order, plus the partial AR-processing index (0035). The admin dashboard parallelizes its 5 KPI queries across separate pooled connections (read_repos.py:86-105).
- Defence-in-depth config validation: Settings rejects boot when REVIEW_TEST_PHONE equals SUPER_ADMIN_PHONE (settings.py:222-238), preventing an app-store reviewer from ever resolving to super_admin, and the effective role is recomputed per-request from SUPER_ADMIN_PHONE rather than trusted from the JWT.
