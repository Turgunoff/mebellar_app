## 1. Mahsulot vizioni va biznes-model

**Woody** (mobil ilovada tarixan *Mebellar* deb nomlangan) — O'zbekiston bozori uchun ikki tomonlama (two-sided) **mebel marketpleysi**. U xaridorlarni (customers) mahalliy mebel ishlab chiqaruvchilar va sotuvchilar (sellers/shops) bilan bog'laydi.

- **Talab tomoni (Customer):** mebelni katalogdan ko'rib chiqadi, savatga qo'shadi, buyurtma beradi (hozircha **Cash-on-Delivery / COD**), sotuvchi bilan buyurtma bo'yicha chatlashadi, sharh qoldiradi.
- **Taklif tomoni (Seller):** do'kon ochadi, tasdiqdan o'tadi (verification), mahsulot joylaydi (AI yordamida fotodan to'ldirish bilan), buyurtmalarni bajaradi, tarif sotib oladi va hamyon (wallet) orqali komissiya to'laydi.
- **Platforma daromadi:** sotuvdan olinadigan **komissiya** (tarifga bog'liq foiz) + premium **tarif** obunalari.

### Monetizatsiya modeli (joriy)

| Manba | Mexanizm | Holat |
|---|---|---|
| Komissiya | Har bir `delivered` buyurtmadan tarifga qarab % (10/7/4/2%) seller hamyonidan yechiladi | ✅ Live |
| Tarif obunasi | Oylik to'lov (kvitansiya + admin moderatsiyasi) | ✅ Live |
| Trial bonus | Birinchi tasdiqda 30-kunlik 0% komissiya plani (acquisition lever) | ✅ Live |

> **Muhim:** Hozir to'lovlar **faqat naqd (COD)** — onlayn to'lov shlyuzlari (Payme/Click) [Phase 3](#14-kelajakdagi-featurelar-roadmap-kesishmasi)da rejalashtirilgan. Komissiya seller hamyonidan yechiladi, xaridor naqd to'laydi.

## 3. Aktyorlar va rollar (RBAC)

| Aktyor | Autentifikatsiya | Imkoniyatlar |
|---|---|---|
| **Guest (mehmon)** | Yo'q | Katalog ko'rish, lokal savat, lokal sevimlilar. Checkout — login talab qiladi |
| **Customer** | Telefon + OTP | To'liq xaridor sirti: savat, buyurtma, chat, sharh, sevimlilar (server) |
| **Seller** | Telefon + OTP + tasdiq | Do'kon, mahsulot, buyurtma bajarish, tarif, hamyon, analitika |
| **Manager (moderator)** | Telefon + OTP, `app_metadata_role` | Admin panelning delegatsiya qilingan sohalari (qarang quyida) |
| **Super-admin** | `SUPER_ADMIN_PHONE` ga mos telefon | To'liq admin: tariflar, hamyonlar, managerlar, sozlamalar, broadcast |

### RBAC mexanikasi (backend-da kuchaytirilgan)

- **Ikki rol:** `super_admin` va `manager`. `super_admin` — faqat `SUPER_ADMIN_PHONE` ga mos kelgan telefon orqali aniqlanadi (JWT claim'ga ishonilmaydi). `manager` — `profiles.app_metadata_role`.
- **Effective role har so'rovda qayta hisoblanadi** (`get_effective_role()`), JWT claim'ga ko'r-ko'rona ishonilmaydi.
- **Scoped moderatorlar:** `app_metadata_permissions` JSONB. `null` = to'liq manager; massiv = quyidagi delegatsiya qilinadigan sohalar bilan cheklangan:
  `orders, products, sellers, shops, customers, reviews, categories, analytics`.
- **Faqat egasi (super_admin only):** `tariffs, wallets, banners, news, notifications, settings, managers`.
- Ruxsatlar **login paytida** (OTP + refresh) JWT'ga yoziladi; o'zgarishlar keyingi login'da kuchga kiradi.

> **Invariant:** Ruxsat (scope) cheki har bir `/admin/*` marshrutida `require_admin` (`scope_for_admin_path`) orqali markazlashtirilgan. Guard'ni unutish — xavfsizlik xatosi.

## 4. Customer domeni

### 4.1 Autentifikatsiya — Telefon + OTP (Eskiz)

- **Parolsiz.** Foydalanuvchi telefon raqamini kiritadi → backend OTP generatsiya qiladi (5 xonali, Eskiz SMS shabloniga bog'langan) → foydalanuvchi kodni kiritadi → access + refresh JWT (HS256) chiqariladi.
- **OTP qoidalari:** 5 xonali kod; per-telefon cooldown (`OTP_REQUEST_COOLDOWN_SECONDS`); urinishlar chegarasi (`OTP_ATTEMPTS_MAX`); amal qilish muddati (`OTP_CODE_EXPIRY_MINUTES`). Kod DB'da **hash**lanib saqlanadi.
- **Eskiz shabloni muqaddas:** SMS matni Eskiz tomonidan oldindan tasdiqlangan; o'zgartirish qayta tasdiqlashni talab qiladi.
- **Bloklangan akkaunt:** har bir gate'da `AccountBlocked` tekshiriladi — OTP request/verify/refresh **403** qaytaradi (401 emas).
- Endpoint'lar: `POST /auth/otp/request`, `POST /auth/otp/verify`, `POST /auth/refresh`, `POST /auth/logout`.

### 4.2 Katalog va qidiruv

- Ochiq (auth talab qilmaydi). `GET /catalog/products` filtrlari: `category_id, subcategory_id, shop_id, color[], min_price, max_price, in_stock, has_delivery, search`; saralash: `newest | price_asc | price_desc`; `limit/offset` paginatsiya.
- Faqat `approved` statusli mahsulotlar xaridorga ko'rinadi.
- Qo'shimcha: `GET /catalog/products/{id}`, `/similar`, `/shops/{id}`, banner va kategoriya daraxti.

### 4.3 Savat (Cart) — Hybrid guest/server + Smart CTA

**Hybrid arxitektura:** savat mijoz auth holatiga qarab ikki backend o'rtasida marshrutlanadi:

| Holat | Saqlash | Manba |
|---|---|---|
| Guest | Lokal **Hive** (`CartItemModel`: nom, rasm, narx, do'kon) | `HiveCartRepository` |
| Logged-in | Server | `WoodyCartRepository` (REST) |

**Aniq biznes-qoidalar:**

- **Login'da merge:** foydalanuvchi kirganda lokal savat elementlari server savatiga **best-effort** ko'chiriladi (`POST /cart/items` har biri uchun; mavjud bo'lmagan mahsulotlar o'tkazib yuboriladi), so'ng lokal savat tozalanadi. Bu `HybridCartRepository._mergeGuestCart()` orqali avtomatik (auth o'zgarishida).
- **Miqdor chegarasi:** har bir qator uchun **1–99**.
- **Bir mahsulot = bir tanlangan rang.** Rang o'zgarishi mavjud qatorni yangilaydi, yangi qator yaratmaydi. Mahsulotda ranglar bo'lsa — rang tanlash **majburiy** (tanlanmasa, validatsiya rang kartochkasiga scroll qiladi).
- **Optimistic update:** UI holati API chaqiruvidan oldin emit qilinadi; xato bo'lsa oldingi snapshot'ga qaytariladi (`CartStatus.mutating → ready | rollback`).
- **Checkout gate:** mehmon checkout'ni bossa to'liq ekranli `AuthScreen` ko'rsatiladi; muvaffaqiyatli login'dan keyin savat allaqachon merge bo'lgan, eng yangi savat qayta o'qiladi va `/checkout`ga o'tiladi.

**Smart CTA (mahsulot detalida):**

- Mahsulot savatda yo'q (qty=0): **"Savatga qo'shish"** (shopping_bag ikonkasi).
- Mahsulot savatda (qty>0): `AnimatedSwitcher` orqali **`[− qty +]` stepper + "Savatga o'tish"** ga aylanadi (deep-link `go('/?tab=cart')`, push emas).
- `−` tugmasi qty=1'da **o'chirish** (trash ikonka)ga aylanadi; `+` qty=99'da o'chiriladi.

### 4.4 Sevimlilar (Favorites)

- Server-da `product_id` + `product_snapshot` (JSONB) sifatida saqlanadi. Endpoint'lar: `GET/POST /favorites`, `DELETE /favorites/{product_id}`.
- Flutter: `FavoritesBloc` optimistic toggle + re-fetch; `Set<String>` id'larni kuzatadi. Har login/logout'da qayta yuklaydi (`authChanges.distinct()`). 401'da lokal kesh tozalanadi. Buzuq snapshot'lar o'tkazib yuboriladi va loglanadi.

### 4.5 Checkout va buyurtmalar (COD)

- **Bir do'kon = bir buyurtma:** `POST /orders` savatni do'kon bo'yicha guruhlaydi va har bir guruh uchun alohida buyurtma yaratadi.
- **Server avtoritar:** narx server tomonida `products` jadvalidan qayta hisoblanadi (savat snapshot'idan **hech qachon**). Snapshot faqat ko'rsatish uchun (≤8192 bayt).
- Buyurtmadan keyin savat best-effort tozalanadi. `ProductNotFound` / `SellerSuspended` xatolari ushlab olinadi.
- Buyurtma status mashinasi (qarang [Appendix A](#appendix-a-status-enumlar-va-holat-mashinalari)): `pending → confirmed → preparing → shipped → delivered`; `cancelled` faqat `pending/confirmed`dan.
- Bekor qilish: `POST /orders/{id}/cancel {reason}`.

### 4.6 Chat — buyurtma bo'yicha

- **Bir buyurtma = bitta chat** (`chats.order_id` UNIQUE). Xaridor birinchi xabarda lazy-yaratadi; sotuvchi chat ocha olmaydi.
- Chat **abadiy OCHIQ** qoladi (arxivlanmaydi). Banner joriy buyurtma statusini aks ettiradi (`delivered` → "Sharh qoldiring" CTA).
- Xabarlar: matn + `attachment_url`. Realtime WebSocket orqali; fallback — ochilishda refresh + FCM foreground push.
- Endpoint'lar: `GET /chats`, `POST /chats {order_id}`, `GET/POST /chats/{id}/messages`, `POST /chats/{id}/read`.

### 4.7 Sharhlar (Reviews)

- `GET/POST /reviews`; sotuvchi javob bera oladi `PATCH /reviews/{id}/reply`.
- Buyurtma `delivered` bo'lgach chat banneri sharh qoldirishni taklif qiladi.

## 5. Seller domeni

### 5.1 Onboarding va verifikatsiya

1. `POST /seller/onboarding` (`business_type, legal_name, contact_phone, shop_name, …`).
2. `POST /seller/verification-docs` (`document_type, storage_path`) → `sellers.verification_status = pending`.
3. Admin ko'rib chiqadi → `approved`/`rejected` (bildirishnoma yuboriladi).
4. **Birinchi tasdiqda** trial bonus avtomatik beriladi (qarang [§7](#7-tarif-subscription-tizimi)).

- VerificationStatus enum: `none (sentinel) | pending | in_review | approved | rejected`.
- `profiles.is_seller_pending` denormalizatsiya qilingan; tasdiqda sinxronlanadi.
- Cold-start'da: agar keshlangan tasdiq flag'i `false` bo'lsa, ilova rejimni customer'ga tushiradi.

### 5.2 Do'kon va mahsulotlar

- Do'kon: `GET/PATCH /seller/shop`. `1 seller = 1 shop`.
- Mahsulot CRUD: `GET/POST /seller/products`, `PATCH /seller/products/{id}`, `archive/restore`, `DELETE`.
- ProductStatus: `draft | pending_review | approved | rejected | archived`. Yangi mahsulot moderatsiyaga tushadi.
- **Atributlar** kategoriya sxemasiga bog'langan (seed: `0011_seed_attributes.py` — 81 ta ta'rif, 168 ta variant).

#### AI fill-from-photos (mahsulotni fotodan to'ldirish)

- `POST /seller/products/ai-suggest {image_urls[]}` → Azure OpenAI Vision (`gpt-5-mini`, reasoning) → `{available, name, description, category_id, subcategory_id, colors, attributes}`.
- Model promptiga **real kategoriya daraxti + atribut sxemasi** joylashtiriladi, shunda u mavjud kalit/qiymatlarni tanlaydi. Ranglar kanonik to'plamga filtrlanadi.
- **Har doim 200 qaytaradi** (`available: false` — o'chirilgan/creds yo'q/xato bo'lsa). **Hech qachon avtomatik saqlamaydi** — faqat formani to'ldirib taklif qiladi.
- Rasm chegarasi: vision modelga maksimum 4 ta foto (cubit'da cheklangan).

### 5.3 Buyurtma bajarish

- `GET /seller/orders`, `GET /seller/orders/{id}`, `PATCH /seller/orders/{id}/status` (status mashinasi bo'yicha).
- `delivered`ga o'tganda komissiya avtomatik yechiladi (qarang [§6](#6-pul-tizimi-wallet-credit-limit-komissiya-cod)).

### 5.4 Analitika, yutuqlar, leaderboard

- `GET /seller/dashboard`, `/analytics`, `/achievements`, `/leaderboard`, `/reviews`.

## 6. Pul tizimi: Wallet, Credit Limit, Komissiya, COD

> Bu platforma daromadining yuragi. Barcha qoidalar ishlab chiqarish kodidan tasdiqlangan (migration `0013`, `0020`, `0027`; `app/services/wallet.py`).

### 6.1 Konseptual model

Naqd (COD) sotuvda **xaridor sotuvchiga naqd to'laydi**, lekin platforma komissiyasi sotuvchining **hamyonidan (wallet)** yechiladi. Hamyon — append-only imzolangan **ledger** (`wallet_transactions`), har qatorda `balance_after`.

Sotuvchi balansi **manfiy** bo'lishi mumkin — kredit limiti chegarasigacha (`floor = -credit_limit`). Floor'dan o'tilsa **48 soatlik grace** boshlanadi; tozalanmasa **suspension** (muzlatish).

### 6.2 Aniq biznes-qoidalar

| Qoida | Qiymat |
|---|---|
| **Grace oynasi** | **48 soat** (`WALLET_DEBT_GRACE_HOURS = 48`, konfiguratsiyalanadigan) |
| **Komissiya foizlari** (tarif bo'yicha) | free **10%** · basic **7%** · pro **4%** · enterprise **2%** (trial **0%**) |
| **Kredit limitlar** (floor = −limit) | free/trial **0** · basic **200 000** · pro **500 000** · enterprise **2 000 000** so'm |
| **Komissiya muzlatish** | Sotib olish vaqtida `order_items.commission_rate`da muzlatiladi (migration 0020) |
| **Komissiya yechish** | **Faqat buyurtma `delivered`ga o'tganda** (`charge_order_commission()`), status flip bilan bir tranzaksiyada |
| **Idempotentlik** | `unique(seller_id, order_id) WHERE type='commission'` — status necha marta o'zgarsa ham bir marta yechiladi |
| **Suspension xatti-harakati** | Suspended seller mahsulotlari katalogda **ko'rinadi** (SEO + sevimlilar saqlanadi), lekin `stock=0` deb ko'rsatiladi; buyurtma yaratish `SellerSuspended` bilan rad etiladi |
| **Avtomatik tiklash** | Balans floor'ga yetganda darhol tiklanadi (grace yoki suspension bekor) |
| **Sweep interval** | `WalletDebtSweeper` har **300s** (konfiguratsiyalanadigan), 100 seller/o'tish |

### 6.3 Soft-freeze holat-mashinasi (ladder)

```
[normal]  balance ≥ -credit_limit
   │  balans floor'dan pasaydi (grace ishlamayapti)
   ▼
[grace]   debt_grace_period_until = now + 48h  →  ogohlantirish bildirishnomasi
   │  48h o'tdi, balans hali floor ostida
   ▼
[suspended]  is_suspended_due_to_debt = true  →  mahsulotlar ko'rinadi lekin sotib bo'lmaydi
   │  balansga ijobiy kredit kirdi (≥ floor)
   ▼
[normal]  darhol tiklanadi  →  qayta-faollashtirildi bildirishnomasi
```

### 6.4 Hamyon endpoint'lari

**Seller tomoni** (`require_user`):
- `GET /seller/wallet` → `WalletSummary` (balance, credit_limit, debt_floor, is_suspended_due_to_debt, debt_grace_period_until, pending_topup, transactions)
- `GET /seller/wallet/transactions?limit=30&offset=0` → paginatsiyalangan ledger
- `POST /seller/wallet/topups {amount, payment_screenshot_path}` → top-up so'rovi
- `GET /seller/wallet/topups` → o'z so'rovlari

**Admin tomoni** (`super_admin only`):
- `GET /admin/wallets/topups?status=...` → kutilayotgan tasdiqlar (seller identifikatori + jonli balans bilan)
- `PATCH /admin/wallets/topups/{id}/approve` → hamyonni kreditlaydi + balans floor'ni o'tsa avto-qayta-faollashtiradi
- `PATCH /admin/wallets/topups/{id}/reject {reason}` → rad etadi + bildiradi
- `GET /admin/wallets/sellers/{id}` → seller hamyon detali
- `POST /admin/wallets/sellers/{id}/adjust {amount: signed, note}` → qo'lda tuzatish (imzolangan: `created_by`, majburiy izoh)

### 6.5 Top-up moderatsiya oqimi

Seller skrinshot + summa yuboradi → `pending` → admin tasdiqlaydi (hamyonga kredit) yoki rad etadi (sabab bilan). Bu oqim tarif kvitansiya moderatsiyasiga **aynan parallel** (bir xil ishonch modeli).

### 6.6 Bildirishnoma turlari (5 ta hamyon hayot-tsikli)

`wallet_grace_started` (isoformat deadline + balans bilan), `wallet_suspended`, `wallet_reactivated`, `wallet_topup_approved`, `wallet_topup_rejected`.

> **UX nozikligi:** seller tomonida grace countdown **minimum 1 soat**ga floor qilingan (`graceHoursLeft`), banner UX'ni falaj qilmaslik uchun (<1h qolsa ham "1 soat" ko'rsatiladi).

## 7. Tarif (Subscription) tizimi

- **Plan modeli:** `code` (unique, immutable, `^[a-z0-9_]+$`), `name`, `price_monthly`, `commission_rate %`, `max_products` (−1 = cheksiz), `max_images_per_product`, `is_recommended`, `features_uz[]/features_ru[]`, `credit_limit`.
- **Default:** har bir seller `free` tarifda boshlanadi.
- **Trial bonus (acquisition lever):** `code='trial'` plani — **0% komissiya, 30 kun, 200 mahsulot, 10 rasm**. Birinchi tasdiqda **aynan bir marta** beriladi (`sellers.first_approved_at` watermark, `IS NULL` guard). Trial plan seller ro'yxatidan yashirilgan (`TariffRepository.list_plans()` `code != 'trial'`).
- **To'lov oqimi:** seller kvitansiya skrinshot yuboradi → admin moderatsiyasi (approve/reject) → obuna faollashadi.
- **Expiry sweeper** (`TariffExpirySweeper`): obunalar tugaganda — limitdan oshган mahsulotlarni arxivlaydi (eng eski avval), do'konni `free`ga qaytaradi, bildirishnoma yuboradi. **5 kun oldin** ogohlantiradi (oyna boshiga bir marta).
- **Admin CRUD:** `POST/PUT/DELETE /admin/tariffs`; kvitansiya moderatsiyasi `GET /admin/tariffs/receipts`, `approve/reject`.
- Receipt status: `none (internal) | pending | approved | rejected | cancelled`.

## 9. Internatsionalizatsiya (i18n) kontraktlari

> Bu kontraktlar yangi developerlarni eng ko'p adashtiradigan joy — shu sababli aniq bayon qilinadi. Tasdiq: `app/domain/i18n.py`, `app/domain/write.py`, `woody_admin/components/admin/product-translations-form.tsx`, migration `0026`.

### 9.1 Locale to'plami

**Aynan uchta til:** `uz` (baseline/default, birinchi), `ru`, `en`. `uz` — kanonik manba.

### 9.2 DB strukturasi

- **Mahsulotlar:** `name`, `description` (kanonik uz) + `name_i18n`, `description_i18n` (JSONB, faqat ru/en override'lar).
- **Subkategoriyalar:** `name` + `name_i18n` (JSONB).
- **Kategoriyalar:** legacy suffix ustunlar `name_uz/name_ru/name_en`, `subtitle/subtitle_ru/subtitle_en`.

### 9.3 "No-'uz'" kontrakti (eng muhim qoida)

- **`TranslationPatch` 'uz' kalitini TAQIQLAYDI** (`ConfigDict(extra='forbid')`). Payload'da `uz` bo'lsa → **422**.
- Faqat `ru` va `en` yoziladigan override'lar; kanonik `uz` matn base ustunlarda yashaydi.
- **Admin frontend hech qachon 'uz' yubormaydi:** `TABS` massivi faqat `[ru, en]`; forma `uz` maydonini generatsiya qilmaydi.

### 9.4 Read-only fallback

- Tarjima yo'q bo'lsa, SQL **kanonik uz**ga qaytadi: `COALESCE(NULLIF(i18n_jsonb->>lang, ''), base_column)`.
- Bo'sh override satr (`''`) → `NULL` deb qaraladi → base'ga fallback.
- **Admin UI:** `uz` matn tablardan **yuqorida read-only** ko'rsatiladi; tarjima endpoint'i orqali hech qachon tahrirlanmaydi.

### 9.5 Merge-patch semantikasi (RFC-7386)

- Mavjud bo'lmagan (absent) kalitlar saqlangan qiymatni o'zgartirmaydi.
- `null`/bo'sh qiymatli kalitlar saqlangan kalitni **o'chiradi**.
- Yakuniy map bo'sh bo'lsa → ustun SQL `NULL` saqlaydi (`{}` emas).
- Legacy `uz` kalitlari eski ma'lumotlarda saqlanadi, lekin patch yangi `uz` yoza olmaydi.

### 9.6 Accept-Language oqimi (end-to-end)

```
Flutter til almashtirish → WoodyApiClient._locale closure
   → har so'rovda Accept-Language sarlavhasi (bare kod: uz/ru/en)
      → backend parse_accept_language() (browser-style "ru-RU,ru;q=0.9" ham, unsupported → uz)
         → catalog_repos COALESCE rezolyutsiyasi
            → admin tarjimalari hech qachon uz'ga tegmaydi
```

- **Field limitlar:** `ProductNameTranslationPatch` ru/en max **400**; `ProductDescriptionTranslationPatch` max **10000**.
- **Konkurent yozuv xavfsizligi:** `ProductWriteRepository.update_translations` `FOR UPDATE` tranzaksiya ishlatadi.

## 10. Akkaunt hayot-tsikli: soft-delete va bloklash

> Migration `0025`. Kaskadli soft-delete + qaytariladigan bloklash uchala repoda shipped.

- **Soft-delete:** `profiles.deleted_at timestamptz` + generated `is_deleted` bool. O'chirilgan qatorlar audit uchun telefonni saqlaydi, lekin raqam qayta ro'yxatdan o'tish uchun **bo'shaydi** (partial unique index: `(phone) WHERE phone IS NOT NULL AND deleted_at IS NULL`).
- **Bloklash:** `blocked_at` + `blocked_reason`, generated `is_blocked`. Bloklash OTP request/verify/refresh'ni to'sadi, **403** `AccountBlocked` qaytaradi. **Qaytariladi** (`blocked_at` tozalanadi).
- **Kaskad:** `ON DELETE CASCADE` FK `profiles.id`'dan: sellers, subscriptions, shops, orders, chats, reviews, favorites, cart_items, device_tokens, notifications, wallet_transactions, wallet_topups, verification_documents. `products → sellers(id)` cascade.

## 11. Tarmoq barqarorligi UX (3-tier)

> To'liq implementatsiya qilingan, lekin avval hech qayerda hujjatlashtirilmagan. Tasdiq: `home_bloc.dart`, `categories_bloc.dart`, `network_error_gate.dart`, `flashscore_network_modal.dart`.

Asosiy ma'lumot ekranlarida (home, kategoriyalar, mahsulot ro'yxati, buyurtmalar) bardoshli uch bosqichli degradatsiya:

### Tier 1 — Graceful (keshdan birinchi paint)
- Keshlangan ma'lumot mavjud bo'lsa, tarmoq chaqiruvidan **oldin** darhol `ready` holat emit qilinadi, so'ng fonda yangilanadi.
- Fon-yangilanish xatosi (ma'lumot ekranda turganda) — **bloklamaydigan** yuqori toast (`Icons.wifi_off_rounded`), faqat `status==ready && error!=null`da.

### Tier 2 — Loading (shimmer)
- Kesh yo'q bo'lsa, `loading` holat → shimmer skeletonlar (`GlassBannerShimmer` aniq shaklni takrorlaydi, mahsulot grid `Shimmer.fromColors`, 1200ms animatsiya).

### Tier 3 — Critical (bloklovchi modal)
- **Qattiq 5 soniyalik ceiling** (`Duration(seconds: 5)`) — Dio'ning 15s connect / 30s receive timeout'idan **qisqa**, shunda o'lik ulanish modalni tez chiqaradi.
- Yuklash muvaffaqiyatsiz **VA** fallback uchun kesh yo'q bo'lsa → bloklovchi `FlashscoreNetworkModal`.
- **Non-dismissible:** `PopScope(canPop:false)` + `barrierDismissible:false`; faqat "Qayta urinish" tugmasi yoki tiklanishda avto-yopilish.
- **Root navigator** (`useRootNavigator:true`) — bottom nav va shell ustidan ko'rsatiladi.
- **Single-owner pop logikasi:** `_modalOpen` flag modal stacking'ni oldini oladi; ichki `BlocListener` `isRecovered=true`da darhol `pop()` qiladi.

### Qo'shimcha qoidalar
- **Kesh TTL'lari:** mahsulot tavsiya 1h, by-id 4h, similar 4h, by-category 1h, banner 6h, kategoriya 24h.
- **Til-scoped kesh:** kalitlarga `@{lang}` qo'shiladi — til almashtirishda eski-til keshi oqib chiqmaydi.
- **Avto-retry:** tarmoq `offline→online` o'tganda VA holat `failure` bo'lsa, refresh fire qilinadi (`NetworkCubit` → `HomeBloc/CategoriesBloc`).
- **Ulanish aniqlash:** `connectivity_plus` (link-state) + `internet_connection_checker_plus` (HEAD-ping reachability, captive-wifi xavfsiz).

## 12. Bildirishnomalar (Notifications + FCM)

- **In-app inbox** + **FCM push**. Endpoint'lar: `GET /notifications`, `PATCH /notifications/{id}/read`, `POST /notifications/read-all`.
- **Dispatch pipeline:** DB trigger qator INSERT qiladi → `NotificationDispatcher` (LISTEN + worker queue + sweep) → FCM push + WebSocket fan-out.
- **FCM klient:** `NoOpFcmClient` (dev/CI default) va `FirebaseFcmClient` (prod, `firebase-admin`). `FCM_SERVICE_ACCOUNT_PATH` o'rnatilganda boot'da real klient tanlanadi. Multicast **500 token/batch**; yaroqsiz tokenlar `device_tokens`dan tozalanadi.
- **Broadcast** (super_admin): `POST /admin/notifications/broadcast {title, body, audience, send_push?}`. Audience: `all_devices` (FCM `news` topic — anonim install'lar ham) | `all` | `sellers` | `customers`.
- **Triggerlar:** seller verifikatsiya, mahsulot moderatsiyasi, chat xabari, tarif hodisalari, hamyon hayot-tsikli (25 ta notification turi — qarang [Appendix A](#appendix-a-status-enumlar-va-holat-mashinalari)).

> **Go-live talabi:** real FCM uchun Firebase service-account JSON + iOS APNs kaliti kerak (qarang [roadmap](../planning/roadmap.md)).

## Appendix B: Kelib chiqishi (Supabase → woody_backend migratsiyasi)

> Tarixiy kontekst. Asl arxitektura qarori `mebellar_v2_tz` (2026-05-01) da hujjatlashtirilgan edi va shu yerda saqlanadi.

Platforma dastlab **Supabase** stekida loyihalashtirilgan edi (Postgres + Auth + Storage + Realtime), Flutter `supabase_flutter` orqali to'g'ridan-to'g'ri ulangan, OneSignal push, Sentry crash, email+parol auth, va Telegram aiogram bot bilan.

**2026-05-31**da Supabase **uchala repodan to'liq olib tashlandi**. Joriy haqiqat:

| Eski (Supabase davri) | Yangi (joriy) |
|---|---|
| Supabase Postgres + RLS | Mustaqil Postgres + asyncpg + Alembic |
| Supabase Auth (email+parol) | Telefon + OTP (Eskiz), JWT HS256 |
| Supabase Storage | Cloudflare R2 (presigned URL) |
| Supabase Realtime (CDC) | O'z WebSocket broker (in-process / Redis) |
| OneSignal | Firebase FCM |
| Sentry | Firebase Crashlytics |
| Telegram aiogram bot | woody_admin paneli (bot rolini qoplaydi) |
| `handle_new_user` trigger | OTP-verify `find_or_create` |

Bu o'tish vaqtinchalik backend ramka, mustaqil scaling va vendor-lock'dan qochishni ta'minladi. `grep -i supabase lib/` endi nol qaytaradi.
