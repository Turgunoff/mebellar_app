## 1. System Overview

**Woody** (historically branded *Mebellar* in the mobile app) is a two-sided (B2B2C) **furniture marketplace** built for the Uzbekistan market. It connects buyers (customers) with local furniture manufacturers and retailers (sellers/shops), with platform operators (admins) moderating the marketplace in between.

- **Demand side — Customer.** Browses the catalog, builds a cart, places orders (**cash-on-delivery** or **online via Payme/Click** — deferred until the seller sets the delivery fee), chats with the seller per order, and leaves product reviews. Guests can browse, keep a local cart, and favorite freely; a login gate (phone + OTP) applies only at checkout.
- **Supply side — Seller.** Opens a shop, passes verification, lists products (with optional AI fill-from-photos and a photo-to-3D AR pipeline), fulfills orders, buys a subscription tariff (Payme self-serve or manual receipt), tops up the wallet / AR tokens online, and pays commission through a wallet ledger.
- **Operations — Admin.** Super-admins and scoped managers moderate sellers, products, orders, reviews, categories, tariffs, wallet top-ups, and broadcast notifications. They can toggle Payme/Click visibility via `app_settings.payment_methods`.

**Monetization** comes from two sources, both live in production:
- **Commission** — a tariff-dependent percentage (free 6% / basic 4% / pro 2% / enterprise 1%; trial bonus 2%) deducted from the seller's wallet when an order reaches `delivered`. For COD the buyer pays the seller in cash; for online Payme the buyer pays at checkout.paycom.uz and the order advances `awaiting_payment → confirmed`. The platform still takes its cut from the seller's wallet ledger on delivery. The descending ladder is the upsell: a higher tier buys a lower rate.
- **Tariff subscriptions** — monthly plans (basic 99 000 / pro 299 000 / enterprise 999 000 so'm) paid via **Payme/Click deep-link** (self-serve, auto-activates on webhook) **or** receipt upload + admin moderation. A 30-day **trial bonus** ("Bonus", 2% commission, 30 products, 3 AI-3D generations) is granted once on a seller's first approval as an acquisition lever.

> Rates and caps live in `woody_backend/app/services/tariffs_seed.py`, which **overwrites** `subscription_plans` on every `woody seed-tariffs` run. Admin-panel edits to a plan are lost at the next seed unless mirrored back into that file.

**Online payments (Payme) are live** — Merchant API webhook (`POST /api/v1/webhooks/payme`, all 6 RPC methods + fiscalization) settles customer orders, seller tariffs, AR-token packs, and wallet deposits. Click is offered in the UI and mints `my.click.uz` checkout URLs, but **has no settlement webhook yet** (payments opened via Click do not auto-confirm). See §4 *Payme payments*.

> **Origin note:** The platform was originally built on Supabase (Postgres + Auth + Storage + Realtime, with `supabase_flutter`, OneSignal, Sentry, and a Telegram bot). On 2026-05-31 Supabase was fully removed from all repos. The current stack is fully independent: own FastAPI backend, own auth (phone + OTP), Cloudflare R2 storage, an in-house WebSocket broker, and Firebase (FCM + Crashlytics + Analytics).

## 2. High-Level Architecture

The platform is a **single monorepo containing four subprojects**. All client surfaces (mobile, admin, marketing) talk to **one backend** — `woody_backend` at `api.woody.uz`. Clients hold no database credentials and use no direct third-party data SDKs; every external integration (SMS, object storage, push, AI) is abstracted behind the backend.

### The four modules

| Module | Role | Domain | Talks to |
|---|---|---|---|
| **mebellar_app** | Flutter mobile app — Customer + Seller in one binary, two modes | mobile (Play / App Store) | `api.woody.uz` (REST + WebSocket) |
| **woody_backend** | The single backend — auth, data, storage, realtime, integrations | `api.woody.uz` | Postgres, R2, Eskiz, FCM, Azure OpenAI, Meshy, Payme, Redis |
| **woody_admin** | Internal moderation / management panel | `admin.woody.uz` | `api.woody.uz` (HTTP only; no DB access) |
| **woody_frontend** | Trilingual marketing landing | `woody.uz` | nothing — pure static marketing, no API calls |

### Topology

```
   Flutter (mobile)   ──►  ┌──────────────────────────────┐  ──► Postgres (asyncpg)
   Customer + Seller       │        woody_backend          │  ──► Cloudflare R2 (presigned)
                           │     FastAPI · api.woody.uz     │  ──► Eskiz (OTP SMS)
   Next.js admin      ──►  │   REST (/api/v1) + WebSocket   │  ──► Firebase FCM (push)
   admin.woody.uz          │                                │  ──► Azure OpenAI (AI suggest)
                           │                                │  ──► Meshy (photo → 3D / AR)
   Next.js landing    ──►  │                                │  ──► Redis (optional: WS broker)
   woody.uz (public)       │                                │  ──► Payme Merchant API (webhook)
                           └──────────────────────────────┘
```

How the modules relate:

- **mebellar_app ↔ woody_backend** — the app speaks only REST (routes under `/api/v1`) plus the Woody WebSocket feed (`wss://api.woody.uz/api/v1/realtime/ws`). The same binary runs in customer or seller mode, switched at runtime via a GetIt scope swap and `Phoenix.rebirth`. Uploads (product images, chat attachments, KYC docs, tariff receipts) go through presigned R2 PUT URLs requested from the backend.
- **woody_admin ↔ woody_backend** — the admin is a pure HTTP client of the backend (it owns no database). All reads/writes flow through a single server-only `apiFetch`; RBAC is enforced server-side by the backend on every `/admin/*` route, with the admin's own guards used only for fast redirects and defence in depth.
- **woody_frontend** is decoupled — it never calls the backend. It uses real app screenshots (generated from the mobile app's integration test) for its phone showcase, but has no runtime dependency on the API.
- **Cross-repo contracts** — the status enums (`OrderStatus`, `VerificationStatus`, `ProductStatus`) and the RBAC role rules + moderator scopes are hand-mirrored across backend, mobile, and admin; the backend (`app/domain/enums.py`, `app/security/rbac.py`) is the source of truth.

**Backend internals** are layered: async FastAPI routers (32 sub-routers under `/api/v1`) → domain services + state machines + background sweepers → asyncpg repositories (each behind a Protocol) → a process-singleton connection pool → Postgres (Alembic-managed). Runtime DB access is **raw asyncpg only**; SQLAlchemy exists solely for Alembic. Auth is own JWT (HS256, access + refresh) minted after Eskiz OTP verification, with the effective role recomputed per request. Realtime is an in-house WebSocket broker that runs in-process for single-worker dev or over Redis pub/sub for multi-worker production. Background sweepers handle the notification dispatcher, tariff expiry, and wallet debt grace/suspension.

## 4. Core Flows

> Documented as implemented in `woody_backend/app` and `mebellar_app/lib` as of 2026-06-18. Money is integer so'm throughout. Times are `TIMESTAMPTZ`.

### 1. Authentication — Phone + multi-language SMS OTP (Eskiz) with Android dual-hash autofill

Passwordless: a phone number plus a 5-digit one-time code is the only credential. The backend mints its own HS256 JWTs (no Firebase Auth, no Supabase). Endpoints live in `app/api/v1/auth.py`; orchestration in `app/services/otp.py`; SMS gateway in `app/clients/eskiz.py`; client flow in `mebellar_app/lib/auth/auth_sheet_controller.dart`.

**Request → send (localized template)**
1. Client `POST /auth/otp/request {phone}` with an `Accept-Language` header (`uz` / `ru` / `en`). The router resolves the language via `Depends(get_lang)` and passes it to `OtpService.request_otp`.
2. The phone is normalized to E.164 (`to_e164`); a non-parseable number → `InvalidPhone` → **422 `invalid_phone`**.
3. **Blocked-account gate (before any SMS):** if a live profile exists with `is_blocked`, raise `AccountBlocked` → **403 `account_blocked`** — a banned account never costs a paid SMS.
4. A 5-digit code is generated (`OTP_LENGTH=5`, bound to the approved Eskiz templates), hashed with HMAC-SHA256 + per-row salt (`hash_code`/`make_salt`), and stored in `otp_codes` with `expires_at = now + OTP_TTL_SECONDS` (5 min).
5. **Atomic cooldown claim (SEC-02):** `OtpRepository.claim_request` upserts/resets the code only when the existing row is older than `OTP_REQUEST_COOLDOWN_SECONDS` (60s). If not claimed, raise `RateLimited(retry_after)` → **429 `rate_limited`** with a `Retry-After` header. This closes the read-then-write race that previously let concurrent requests each dispatch a paid SMS.
6. The localized message is selected by `Settings.eskiz_template_for(lang)` (uz is the fallback for any unsupported locale), the literal `{otp}` placeholder is substituted, and `EskizClient.send_sms` dispatches it. Eskiz requires a digits-only `mobile_phone` (no `+`/spaces); the bearer token is fetched lazily, cached in memory, and refreshed once on a 401 then retried.
7. The endpoint returns `{sent: true, cooldown_seconds}`; the client starts a resend countdown from that value.

**Retriever autofill (dual-hash logic, Android) — `_listenForSmsCode`**
- The Eskiz templates each end with the literal 11-char string **`mH1HhnJpGqi`** — this is the SMS Retriever app-signature hash for the **Play App Signing key** of `com.mebellar.app`. Both backend and app hard-code it (`Settings.ESKIZ_MESSAGE_TEMPLATE_*` ↔ `AuthSheetController._playAppSignatureHash`); they must stay byte-identical or autofill silently breaks.
- When the OTP is requested the client starts listening (`smart_auth`), choosing the API by **this running build's** app-signature hash:
  - **Play-installed builds** — signature equals `mH1HhnJpGqi` (matches the template suffix), so `getSmsWithRetrieverApi()` delivers the code **zero-tap**, no dialog.
  - **Debug / sideloaded-release builds** — a different signing key (debug = `yaRHQKhlEo9`), so the silent Retriever can never fire; they fall back to the hash-free `getSmsWithUserConsentApi()`, which shows the system "read this message?" dialog before filling.
- **Two-hash rationale:** the silent Retriever path only fires when the SMS suffix hash matches the *installed* build's signing-key hash. Production (Play) builds carry the Play signing key, so they get the seamless path; locally signed builds would silently never autofill, so they degrade to the User Consent dialog instead of appearing broken.
- Either path writes into `otpCtrl`, which trips the pin field's listener and auto-submits.
- **iOS:** no Retriever — QuickType fills the field via `AutofillHints.oneTimeCode` inside an `AutofillGroup` (`otp_step.dart`).
- **Russian edge case:** the RU template is Cyrillic and exceeds 140 bytes (2 SMS segments), so Retriever can't fire for it — Russian users get the User Consent dialog even on Play builds.

**Verify → JWT issue — `verify_otp`**
8. Client `POST /auth/otp/verify {phone, code}`.
9. **Atomic attempt counting (SEC-01):** `OtpRepository.bump_and_get` increments `attempts` and reads the row in one statement *before* comparison, so concurrent guesses can't all see a stale low count and brute-force the 5-digit code. `attempts > OTP_MAX_ATTEMPTS` (5) → delete row → `OtpAttemptsExhausted` → **429**; expired → delete → `OtpExpired` → **410**; wrong code → `InvalidCode` → **401** (and exhaustion if it was the last allowed attempt).
10. On success the row is consumed (deleted). `find_by_phone` returns **live rows only** — a soft-deleted profile keeps its phone (a partial index frees the number), so a re-login mints a **fresh empty profile** rather than resurrecting the dead one; the old row keeps its order history.
11. Blocked re-check at verify too (the block may have landed between request and verify). Profile is created if absent, or `mark_verified` if previously unverified.
12. `_issue_token_pair` mints `(access, refresh)`. **Admin TTL:** if `get_effective_role(...)` resolves a role (super_admin via `SUPER_ADMIN_PHONE` match or stored manager), the access token gets `JWT_ADMIN_ACCESS_TTL_SECONDS` (1h) instead of the normal `JWT_ACCESS_TTL_SECONDS` (15 min) — the admin panel can't silently refresh mid-render. The refresh `jti` + `exp` are persisted to `refresh_tokens`. `expires_in` mirrors the actual access TTL.

**Refresh / logout — `refresh`, `logout`**
13. `POST /auth/refresh {refresh_token}` verifies a token of `token_type=refresh` (an access token replayed here is rejected). Identity (role, permissions, phone) is **re-resolved from the DB**, never trusted from the old claims, so demotions/blocks/soft-deletes take effect at the next rotation.
14. **Stolen-token defenses:** presenting an already-revoked `jti` triggers `revoke_all_for_user` (scorch the whole chain). A conditional `claim_revoke` (SEC-04) ensures exactly one of two simultaneous refreshes of the same unrevoked `jti` wins; the loser is treated as theft and the chain is scorched. Soft-deleted/blocked accounts also revoke-all → `InvalidRefreshToken` / `AccountBlocked`.
15. `POST /auth/logout {refresh_token}` revokes a single `jti`; idempotent (no-ops on unknown/already-revoked).

**Token format (PyJWT, HS256):** payload `{sub, phone, role, token_type, jti, iat, exp, iss, aud}`; `iss`/`aud` verified on decode. The JWT carries the raw `app_metadata.role`, but the **effective role is recomputed every request** via `get_effective_role()` — never trusted from the JWT for a privilege decision.

**App Store / Play review bypass number:** when both `REVIEW_TEST_PHONE` and `REVIEW_TEST_OTP` are configured, that single number short-circuits both endpoints: `request_otp` returns the normal cooldown without touching the OTP table or sending an SMS (the reviewer can't receive it), and `verify_otp` accepts the fixed `REVIEW_TEST_OTP` via constant-time `hmac.compare_digest`, then runs the **same** find-or-create + blocked re-check + token-mint path as a real login. The bypass is **off by default** (both keys must be set) and `Settings` refuses to boot if `REVIEW_TEST_PHONE == SUPER_ADMIN_PHONE` (which would hand a reviewer super-admin).

> Eskiz templates are sacred: any change to `ESKIZ_MESSAGE_TEMPLATE_{UZ,RU,EN}` (including the trailing `mH1HhnJpGqi` hash) requires re-approval on the Eskiz dashboard, and `OTP_LENGTH` is bound to the approved string.

### 2. Roles & Permissions — customer / seller / admin

There are **two RBAC roles** in the backend (`app/security/rbac.py`): `super_admin` and `manager`. "Customer" and "seller" are not RBAC roles — they are the *same* authenticated end-user identity, distinguished by what data they own. Every authenticated request resolves to an `AuthUser` (`app/deps.py`); the three guards are `require_user`, `require_admin`, and `require_role(...)`.

**Customer**
- Any authenticated `AuthUser` with a profile (guarded by `require_user`). No special role.
- Can: browse the public catalog (guest, no auth), manage cart/favorites (`/cart/*`, `/favorites`), get a checkout `/orders/quote`, place orders (`POST /orders`), list/detail their own orders, **self-cancel only a `pending` order** (`POST /orders/{id}/cancel`), review a delivered item once (`POST /reviews`), open/post in per-order chats, register FCM device tokens.
- Gating: every customer query is scoped to `user_id` from the JWT `sub`; there is no cross-user access. Order detail/cancel/review re-verify ownership server-side.

**Seller**
- Also an authenticated `AuthUser` — *becomes* a seller by owning a `sellers` + `shops` row. Endpoints under `/seller/*` use `require_user`, then `_require_shop(user, repo)` → **404 `shop_not_found`** when the caller has no shop. The seller's `seller_id` is the user UUID, never a request parameter (no IDOR).
- Can: onboard, submit KYC verification docs, manage their shop + products (create/update/archive/restore/delete, scoped to their `shop_id`), set order status forward + cancel + set the delivery fee, run AI product fill, manage wallet top-ups + view ledger, subscribe to tariffs + upload receipts, reply to reviews, run the AR photo-to-3D scan.
- Gating: product/order writes are shop-scoped in SQL (`EXISTS … pr.shop_id = $shop` plus a defense-in-depth `NOT EXISTS other shop`); a debt-suspended seller is blocked from product creation (**403 `wallet_suspended`). The Flutter shell additionally demotes to customer mode at boot if the cached seller-approval flag is false.

**Admin (super_admin / manager)**
- Resolved per request via `get_effective_role()`:
  - **super_admin** — granted **only** to the phone in `SUPER_ADMIN_PHONE` (digit-compared via `normalize_phone`). A stored `role='super_admin'` with a mismatched phone is stripped to nothing.
  - **manager** (moderator) — `profiles.app_metadata_role = 'manager'`. Anything else → `None` → guard returns **403**.
- **Moderator scopes (granular):** `profiles.app_metadata_permissions` (jsonb) — `NULL` = full moderator (every delegable area); `["products", …]` = scoped to listed areas only. Delegable areas (`MODERATOR_SCOPES`): orders, products, sellers, shops, customers, reviews, categories, analytics. `settings` and `managers` are **owner-only** and never delegable.
- **Centralized enforcement:** `require_admin` derives the scope from the request path (`scope_for_admin_path`) and checks `has_permission` — super_admin and full managers pass, scoped moderators only on granted areas. Every admin router gets scope gating for free. `require_role("super_admin")` is a factory used at decorator-application time for owner-only operations (e.g. tariff plan CRUD, manager management).
- The super_admin manages moderators via `/admin/managers` (create is an upsert by phone, so a brand-new moderator can OTP-login to the panel immediately). Permissions ride in the JWT (set at login, carried through refresh) so a change takes effect at the moderator's next sign-in; `/me` always returns the *fresh* DB permissions for nav gating.

> The path→role rules + scope list are duplicated in `app/security/rbac.py` and the admin's `lib/auth/roles.ts` — they must be changed in lockstep.

### 3. Order lifecycle — cart → quote → place → accept → deliver → settle → review-lock

**Cart (guest local Hive → merge on login)** — `mebellar_app/lib/shared/repositories/hybrid_cart_repository.dart`
1. The cart is hybrid: `HybridCartRepository` routes to a **local Hive cart** (guests) or the **backend cart** (`/cart/items`, signed-in) based on session state. Guests add freely with no auth; the login gate is only at checkout.
2. On the guest→signed-in transition, `_mergeGuestCart()` replays the local rows into the server cart (the backend upsert increments quantities — a union, not a toggle), best-effort per item so one unavailable product can't block the rest, then empties the local cart. On sign-out the active backend swaps back to local; the server cart is left intact for the next login.

**Quote (server-computed invoice)** — `POST /orders/quote` → `CustomerOrdersRepository.quote`
3. The checkout screen previews `{subtotal, delivery_fee, installation_fee (potential), installation_selected}`. Pricing is re-derived server-side via the same `_compute_invoice` path that `create()` uses, so the preview can never lie. Delivery applies to every line whose product `has_delivery` (price × qty); installation is the *potential* total and only becomes an applied charge when the customer toggles `want_installation`. Both fees are always server-derived, never client-supplied.

**Place** — `POST /orders` → `CustomerOrdersRepository.create`
4. Pricing/fees are re-derived again at write time (client values ignored). **One order = one shop:** mixing shops → `MultiShopCartNotSupported` (the app already splits the cart into one checkout per shop); this single-shop invariant is what disables the multi-shop IDOR/commission-loss cluster.
5. A single `orders` row is inserted with `status='pending'`, `total_amount = subtotal + delivery_fee + installation_fee`, `delivery_fee`, `installation_fee`, `installation_requested`. Each `order_items` line freezes a snapshot: `price`, `commission_rate` (from the shop's plan at purchase time), `delivery_fee`, `installation_fee`.
6. The router clears the cart only *after* a successful return, so a failed insert can't half-empty the cart.

**Seller accept + delivery-fee lock** — `PATCH /seller/orders/{id}/status`, `…/delivery-fee` → `set_status`, `set_delivery_fee`
7. **Delivery-fee lock:** the seller may set/change the delivery fee **only while the order is `pending`**. The row is locked `FOR UPDATE` for the whole check-then-write; once the seller accepts (confirmed and beyond) the invoice is locked and a fee edit raises `OrderNotPending` → **409**. The new total is re-based in the same statement: `new_total = old_total - old_delivery_fee + new_fee`. The customer is notified via the `orders_notify_delivery_fee_set` trigger (committed in the same transaction).
8. **State machine** (`app/domain/order_policy.py`, mirrored by Flutter `SellerOrderTransitions`): forward lifecycle `pending → confirmed → preparing → shipped → delivered` (confirmed may jump straight to shipped; online payment lands on `awaiting_payment` until paid, then advances to `confirmed`). A seller may cancel from any non-terminal state; a customer may self-cancel only while `pending`. `delivered` / `cancelled` are terminal. Illegal moves raise `IllegalOrderTransition` → **409**. Transitions are validated inside the open transaction so the `FOR UPDATE` lock releases on rollback.

**Delivery SLA (production deadline)** — `stamp_order_deadline` + `OrderSLASweeper`
8a. **Clock starts at `confirmed` only.** Checkout inserts `deadline_at = NULL`. The SLA timer is stamped in the *same transaction* as the transition to `confirmed` — COD via customer fee approval (`CustomerOrdersRepository.approve_fee_adjustment`), online via Payme perform (`awaiting_payment` → `confirmed` + paid), or a seller `set_status` move into `confirmed`. `stamp_order_deadline` reads each line item's `products.production_time_days`, parses the free-text window with `parse_max_production_days` (max of all integers; default **5** days when unparseable), and sets `deadline_at = now() + that many days`. Idempotent: a row that already has `deadline_at` is left alone.
8b. **`OrderSLASweeper`** (hourly, `ORDER_SLA_ENABLED`): selects in-flight rows (`confirmed|preparing|shipped`) with `is_delayed = false` and `deadline_at < now()`, flips `is_delayed = true`, and inserts a `seller_order_delayed` notification for the shop's seller (FCM rides the existing dispatcher).
8c. **Admin "Kechikkan" view** (`GET /admin/orders?delayed=true`): returns only *active* delayed orders — `is_delayed = true AND status NOT IN ('delivered', 'cancelled')`. The list KPI `stats.delayed` uses the same exclusion so resolved history does not inflate the red-zone count. The `is_delayed` flag itself is retained on terminal rows for audit.

**SLA Penalty & Enforcement** — soft demotion + hard suspend (migration 0087)
8d. **Soft penalty (`sellers.sla_penalty_multiplier`, default `1.0`):** scales public catalog ranking. Values below `1.0` demote the shop in `newest` / `popular` / `recommended` (and act as a tiebreaker on price sorts). Catalog SQL multiplies popularity and recommended scores by `COALESCE(se.sla_penalty_multiplier, 1.0)` and leads relevance `ORDER BY` with that expression `DESC`.
8e. **Hard penalty (`sellers.is_suspended_due_to_sla`, default `false`):** moderator-toggled via `PATCH /admin/sellers/{id}/sla-suspend` (`{suspended, sla_penalty_multiplier?}`). While set, `SellerWalletRepository.activity_block_reason` returns `seller_suspended_sla` and seller mutations (create/update product, accept order, set status / delivery fee) return **403**. Catalog stock CASE and checkout pricing treat SLA suspend like debt suspend (effective stock 0 / unpurchasable). Cash SLA fines use the existing admin wallet `adjustment` path — no separate fine endpoint.
8f. **Admin UI:** seller detail shows an SLA badge + suspend toggle + multiplier control; copy points moderators to `/wallets` for monetary adjustments.

### 4b. Payme payments (live) + Click (link-only)

**Deferred customer checkout** — place-order stores the method; charge happens later
1. Customer picks `cash | payme | click` at checkout (`CheckoutCubit`). `POST /orders` stores `payment_provider` / `payment_status=unpaid` and leaves the order `pending` — **no** Payme deep-link is minted at place-order time.
2. Seller accepts and proposes the exact delivery fee; customer approves (`approve_fee_adjustment`):
   - **cash** → `confirmed` (+ SLA `deadline_at` stamped).
   - **payme / click** → `awaiting_payment` (SLA clock does **not** start yet).
3. Customer taps **Pay** on order detail (`_PayNowBar`) → `POST /orders/{id}/pay/{payme|click}` → `PaymentLinkService` returns a hosted checkout URL → app marks a `PendingPayment` and opens it via `url_launcher` (`LaunchMode.externalApplication`).
4. On return / cold start, `PaymentRecoveryGate` polls settlement; realtime / refetch drops `awaiting_payment` once paid so the Pay bar disappears.

**Payme Merchant API** — `POST /api/v1/webhooks/payme` (`app/api/v1/payme_webhook.py` → `PaymeMerchantService`)
5. Public JSON-RPC endpoint (HTTP Basic = `PAYME_MERCHANT_KEY`; login `Paycom` or `PAYME_MERCHANT_ID`). Always HTTP 200 with `{result}` or `{error}`.
6. All **six** classic methods are implemented: `CheckPerformTransaction`, `CreateTransaction`, `PerformTransaction`, `CancelTransaction`, `CheckTransaction`, `GetStatement` (`app/services/payme_merchant.py` + `payme_repos.py`).
7. **Strict order gate (unified with link minting):** CheckPerform / Create accept an order **only** when `status == 'awaiting_payment'` AND `payment_status == 'unpaid'`. A still-`pending` order (fee not set) returns Payme `-31050` (`invalid_account` / not payable) — same rule as `POST /orders/{id}/pay/payme`.
8. Account fields (cabinet-configurable): `order_id`, `ar_purchase_id`, `subscription_id` (= `subscription_receipts.id`), `deposit_id`. Amounts are **tiyin**.
9. **Fiscalization:** `CheckPerformTransaction` returns `detail.receipt_type` + line items (product MXIK / package codes, delivery + installation lines, VAT from `PAYME_VAT_PERCENT`) for Soliq. Dedicated MXIK env keys cover AR / subscription / wallet service lines.
10. **`PerformTransaction` settlements** (atomic with the tx state flip):
   | Target | Intent table | Side-effect |
   |---|---|---|
   | Order | `orders` | `payment_status=paid`, provider=`payme`; if status was `awaiting_payment` → `confirmed` + `stamp_order_deadline` |
   | AR tokens | `ar_token_purchases` | credit tokens + `paid` |
   | Tariff | `subscription_receipts` | `activate_subscription_receipt` |
   | Wallet | `wallet_deposits` | `apply_wallet_delta` + deposit `paid` |
11. **`CancelTransaction` after perform (refund):** state 2 → −2. For an **order** target (unless already `delivered` → `-31007`), the same DB transaction sets `payment_status='refunded'`, `status='cancelled'`, `cancel_reason_code='payment_refunded'`, clears `is_delayed`, and writes a human `cancellation_reason` — unwinding the lifecycle like a normal cancel. Subscription / wallet / AR targets revert their credits as before.
12. Checkout deep-link shape: `{PAYME_CHECKOUT_BASE}/{base64(m=…;ac.*=…;a=<tiyin>)}` (prod default `https://checkout.paycom.uz`).

**Seller self-serve rails** (same `PaymentLinkService` + recovery gate)
13. `POST /seller/tariff/pay`, `POST /seller/ar-tokens/buy`, `POST /seller/wallet/deposit` — body carries `provider: payme|click`; app opens the URL and polls `…/status` / `PaymentRecoveryGate` on resume. Manual P2P (screenshot → admin approve) remains as a parallel path for tariff and wallet.

**Click** — deep-link only today
14. `PaymentLinkService._click_url` mints `https://my.click.uz/services/pay?…`. Admin can toggle Click via `payment_methods`. **There is no Click Prepare/Complete webhook** — choosing Click creates a pending intent that never auto-settles until a merchant callback is built. Treat Payme as the only live auto-settlement rail.

**Delivered → commission / wallet settlement** — `charge_order_commission` (`app/services/wallet.py`)
9. **Delivery is the completion event:** the first time an order transitions to `delivered` (`status == 'delivered' and previous != 'delivered'`), the commission frozen on the order items is debited from the seller's wallet **in the same transaction** as the status flip.
10. Commission = `ROUND(SUM(price × quantity × commission_rate / 100))` over the shop's lines. A zero-rate plan would produce **no ledger row** — note that no seeded plan is currently zero-rate (the trial bonus is 2%, not 0%), so this branch is dormant unless an admin sets a rate to 0. The debit funnels through `apply_wallet_delta` (the single wallet choke point), which is **idempotent** via the partial unique index `wallet_tx_commission_once_idx` — a status flap through `delivered` charges exactly once.

**Review lock**
11. A review is allowed only for a **delivered** order line the caller bought: `ReviewsRepository.create` resolves `order_item → product/shop/order`, verifies `user_id` ownership (→ `OrderNotFound`), requires `status == 'delivered'` (→ `ReviewNotAllowed` / **409**, checked app-side for a clean error ahead of the DB trigger), and a unique constraint enforces one review per order item (→ `ProductAlreadyReviewed`). The "rated" state is backend-derived; the app surfaces the in-app review prompt for 4★+.

### 4. Tariff / trial / wallet soft-freeze + grace

**Tariffs & trial**
- Every seller is on the `free` plan by default. Plans (`subscription_plans`) carry `commission_rate`, `max_products`, `max_images_per_product` (`-1` = unlimited), price, and localized features. Admin owns plan CRUD (`require_role("super_admin")`) and receipt moderation.
- A seller subscribes by **Payme/Click deep-link** (`POST /seller/tariff/pay` → auto-activate on Payme `PerformTransaction`) **or** by uploading a payment receipt (`/seller/tariff/...`); admin approves/rejects the manual path. Approval stamps `subscriptions.expires_at`. A 30-day first-approval **trial bonus** ("Bonus" plan) drops commission to **2%** for the window — down from the free plan's 6% — and unlocks sets, 30 products, and 3 AI-3D generations. It is never purchasable (price 0) and renders only as the current-plan card.
- **Tariff expiry sweeper** (`app/services/tariff_expiry.py`, same asyncio-loop shape as the wallet sweeper): every `approved` subscription whose `expires_at` has passed is flipped to `expired`, the shop is repointed at `free` via the audited `admin_set_shop_plan`, products over the free limit are archived, and the seller is notified. Sellers near expiry get a one-shot `tariff_expiring` notification (deduped by expiry date).

**Wallet soft-freeze + 48h grace** — `app/services/wallet.py`
- Money is integer so'm; `credit_limit` is a non-negative magnitude and the balance floor is `-credit_limit` (free tier 0 → floor 0; pro 500 000 → floor −500 000). Commission is the only automatic debit.
- Every balance mutation funnels through `apply_wallet_delta()` inside the caller's transaction: it locks the seller row `FOR UPDATE`, appends an immutable `wallet_transactions` ledger row with the running `balance_after`, updates `wallet_balance`, and re-evaluates the debt state machine — nothing else writes the balance.
- **Soft-freeze ladder** (`_recalc_debt_state`):
  1. `balance >= floor` → normal service. Recovery is **instant**: any credit that lifts the balance back to the floor clears `is_suspended_due_to_debt` + `debt_grace_period_until` and fires a reactivation notification.
  2. `balance < floor` and no clock running → start a **48h grace window** (`WALLET_DEBT_GRACE_HOURS`), set `debt_grace_period_until`, send a warning notification with the shortfall + deadline. Sinking below the floor only *starts* the clock; it never freezes immediately.
  3. Grace lapses still below the floor → `is_suspended_due_to_debt = true` (flipped by the sweeper). Suspended products **stay visible** in the catalog but report stock 0 / unpurchasable (the order-create pricing path also raises `SellerSuspended` for stale clients).
- **`WalletDebtSweeper`** (default 5 min, `WALLET_DEBT_ENABLED`) is the time half of the machine and runs recovery-first each pass so a recovered seller is never frozen in the same sweep: `_reactivate_recovered` (e.g. a plan upgrade raised `credit_limit`), `_suspend_lapsed` (grace window passed), `_start_grace_overdrawn` (a tariff *downgrade* lowered the floor under the balance — gives the same grace window, not an instant freeze). Each step re-locks and re-checks under `FOR UPDATE` so a between-scan recovery clears the flags instead of freezing.
- **Top-ups:** seller can (a) self-serve via Payme/Click (`POST /seller/wallet/deposit` → Payme webhook credits) or (b) submit `{amount, payment_screenshot_path}` → `pending`; admin approves (credits via `apply_wallet_delta` type `topup`, notifies) or rejects (with reason, notifies). Admin can also post a signed manual `adjustment` through the same choke point.

### 5. Chat + FCM notifications (per-chat push tag, read receipts)

**Per-order chat** — `app/services/chat_repos.py`, shared Flutter module `lib/shared/chat/`
- One `chats` row per `order_id` (UNIQUE). The **customer lazy-creates** the row on first message; the **seller can never spawn a chat**. Chat stays open forever, even after delivered/cancelled — the status banner reflects the current order status (with a "leave a review" CTA on delivered orders, customer side).
- `post_message` is the single source of truth for the unread bump: it inserts the message and increments the **other** side's counter (`seller_unread_count` when a customer sends, vice versa) plus stamps the last-message snapshot. Chat no longer persists to the `notifications` table (the FCM push is sent directly from the app layer).

**Read receipts** — `mark_read`
- `POST /chats/{id}/read` zeroes the reader's own unread counter and stamps `read_at = now()` on all unread messages from the **other** side.
- When something actually changed (and not a self-chat), the sender is sent a `chat_read` realtime event over the WebSocket so their chat-list receipt flips live from delivered (✓) to read (✓✓) instead of lagging until the next refetch.

**FCM new-message push (per-chat tag + dismiss-on-read)** — `_push_chat_message` + `app/clients/fcm.py`
- After persistence + WebSocket delivery have committed, `_push_chat_message` fans a best-effort push to the recipient's `device_tokens` (a push failure never 500s the POST). The payload is built by `build_chat_push`.
- **Per-chat collapse:** the push carries `android_tag = "chat:{chat_id}"` and `thread_id = str(chat_id)`. On Android the tag collapses repeat messages from one chat into a single tray entry; on iOS `apns-collapse-id` + `Aps.thread_id` group/keep-latest. The tag format **must** match the Flutter side (`PushService.chatNotificationTag`) so the app can **cancel a chat's tray notifications once it's read**.
- The real `FirebaseFcmClient` offloads each send to a worker thread (firebase-admin is sync), chunks tokens 500/multicast, and returns `Unregistered`/`SenderIdMismatch` tokens which are pruned from `device_tokens`; transient failures are logged and the token kept. `NoOpFcmClient` is the dev/CI default (selected at boot when `FCM_SERVICE_ACCOUNT_PATH` is unset).
- General order/fee/verification/moderation pushes flow through the separate `NotificationDispatcher` (LISTEN + sweep), which also publishes to the realtime broker; those use no `android_tag`/`thread_id`. Realtime degrades gracefully — the app falls back to refresh-on-open + FCM foreground push if a socket event doesn't arrive.
## 5. Core Data Models

The schema is Postgres (asyncpg at runtime; Alembic for migrations). The baseline (`0001_baseline_schema.sql`) created 29 tables with all Supabase-specific bits stripped (no RLS, no `auth.users` FKs, no realtime publication, no pg_net triggers). `profiles` is the canonical user table; Python creates rows at OTP-verify time. All timestamps are `TIMESTAMPTZ`. Status-like columns are `text` + `CHECK` constraints, never DB enums.

### Identity & users

- **`profiles`** — canonical user row. `id` (uuid PK), `full_name`, `phone`, `preferred_language` (default `uz`), `avatar_url`, `is_seller_pending`, `is_deleted`, `created_at`/`updated_at`. RBAC role + scopes live here as `app_metadata_role` / `app_metadata_permissions` columns (added in later migrations; `phone` is UNIQUE). A profile is a customer by default; becoming a seller adds a `sellers` row.
- **`sellers`** — seller extension, `id` PK **references `profiles(id)`** (1:1). `verification_status` (default `pending`), `business_type`, `legal_name`, `contact_phone`/`contact_email`, `telegram_username`, `rejection_reason`, passport paths. Wallet columns (migration 0027): `wallet_balance` (signed so'm), `credit_limit` (≥0 floor magnitude), `is_suspended_due_to_debt`, `debt_grace_period_until`. `first_approved_at` (migration 0020) gates the one-time trial bonus. SLA penalties (migration 0087): `sla_penalty_multiplier` (float, default `1.0` — soft catalog demotion) and `is_suspended_due_to_sla` (bool, default `false` — hard activity block, moderator-toggled).
- **`shops`** — one per seller, `seller_id` UNIQUE → `sellers(id)`. `name`, `address`, `description`, `logo_url`/`cover_url`, `brand_color`, `working_hours` (jsonb), `latitude`/`longitude`, `is_active`, `plan_id` → `subscription_plans(id)`, and `visibility` (`public | hidden | unlisted`, the third added in 0024). A storefront query treats `unlisted` as link-only and `hidden` as fully closed.
- **`seller_verifications`** / **`verification_documents`** — verification state machine (`none|pending|in_review|approved|rejected`) and uploaded document storage paths, both keyed on the seller profile id.

### Catalog: categories, products, attributes

- **`categories`** — `id`, `name`/`name_uz` (required) + `name_ru`, `subtitle`, `image_url`/`icon_url`, `sort_order`, `is_active`. Seeded in 0005.
- **`subcategories`** — `category_id` → `categories`, `name`.
- **`products`** — core listing. `category_id` (required), `subcategory_id` (nullable), `shop_id`, `seller_id` (required). `name`, `description`, `price numeric(12,2)`, `stock`, `images text[]`, `colors text[]` (GIN-indexed), and a free-form `attributes jsonb` blob. Typed logistics fields: `width_cm`/`height_cm`/`depth_cm`, `material`, `production_time_days`, `has_delivery` + `delivery_price`, `has_installation` + `installation_price`, `warranty_months`. `status` ∈ `draft|pending_review|approved|rejected|archived` with `rejection_reason`. **AR fields** (0034): `ar_video_url`, `ar_model_url`, `ar_status` (`none|processing|pending_review|approved|rejected`), `ar_rejection_reason`; `ar_meshy_task_id` (0035) + `ar_error_reason` (0036) added for the Meshy photo-to-3D pipeline.
- **`product_variants`** / **`product_images`** — per-variant SKU/color/price and ordered image rows (the live app primarily uses `products.images[]`; these tables back richer variant/image modeling).
- **`attribute_definitions`** — per-category (or per-subcategory, XOR-constrained) attribute schema: `key`, `label_uz`/`label_ru`, `data_type` ∈ `select|multiselect|number|text|bool`, `unit`, `is_required`, `sort_order`. UNIQUE per (category, key).
- **`attribute_options`** — allowed values for a `select`/`multiselect` definition: `value`, `label_uz`/`label_ru`. Seeded in 0011 (81 defs + 168 options across 8 categories); reshaped for beds in 0012. Dimensions are stored both as typed `products.*_cm` columns and (per-piece, for sets) inside `products.attributes` jsonb.

### Cart & favorites

- **`cart_items`** — `(user_id, product_id)` UNIQUE, `quantity` (1–99 CHECK), `product_snapshot jsonb`. (Hybrid local-Hive + server cart; this is the server side, merged on login.)
- **`favorites`** — `(user_id, product_id)` UNIQUE, `product_snapshot jsonb`.

### Orders, items, reviews

- **`orders`** — `user_id` → `profiles`, `total_amount numeric(12,2)` (grand total = subtotal + fees since 0028), `status` (default `pending`; lifecycle includes `awaiting_payment|confirmed|preparing|shipped|delivered` + cancelled), `delivery_address`. Invoice fees (0028): `delivery_fee`, `installation_fee`, `installation_requested`. Post-placement fee negotiation: `proposed_delivery_fee`, `fee_adjustment_note`, `fee_adjustment_status` (`pending_customer|approved|rejected`). Cancellation (0030): legacy `cancellation_reason` plus structured `cancel_reason_code` + `cancel_reason_text`. Payment (0068+): `payment_provider` (`cash|payme|click`), `payment_status` (`unpaid|paid|refunded`), `payme_receipt_id`. Delivery SLA (0086): `deadline_at TIMESTAMPTZ` (nullable until `confirmed`) and `is_delayed BOOLEAN NOT NULL DEFAULT false` (sweeper-set; terminal statuses stay out of the admin delayed filter).
- **`order_items`** — `order_id`, `product_id`, `quantity` (>0), `price numeric(12,2)`, `color_slug`. Frozen-at-purchase snapshots: `commission_rate` (0020), `delivery_fee`/`installation_fee` (0028).
- **`cancellation_reasons`** — catalogue of predefined reasons per `role` (`customer|seller`) with `title_uz/ru/en`, `code`, `sort_order`. Each role carries an `other` code (UNIQUE on (role, code)).
- **`reviews`** — one per `order_item_id` (UNIQUE). `order_id`, `product_id`, `shop_id` (resolved by trigger), `customer_id`, `rating` (1–5 CHECK), `comment`, `seller_reply` + `seller_replied_at`. A DB trigger enforces the order is `delivered` and the reviewer is the buyer before insert.
- **`payme_transactions`** — Merchant API ledger (0053+): Payme `id`, `state` (−2/−1/1/2), amounts in tiyin, `target_kind` (`order|ar_tokens|subscription|wallet_deposit`) + target FK, create/perform/cancel times. Drives idempotent `PerformTransaction` / `CancelTransaction`.

### Chat & notifications

- **`chats`** — one per `order_id` (UNIQUE). `customer_id`, `shop_id`, `last_message_at`, `last_message_preview`, `customer_unread_count`/`seller_unread_count`.
- **`chat_messages`** — `chat_id`, `sender_id`, `sender_role` (`customer|seller`), `body` (≤4000) and/or `attachment_url` (at least one required), `read_at`. `mark_chat_read(chat_id, user_id)` clears counts + stamps `read_at`.
- **`notifications`** — `user_id`, `title`, `body`, `type` (large CHECK enum: order lifecycle, seller events, fee adjustments, `admin_broadcast`, `chat_message`, tariff lifecycle, wallet lifecycle…), `is_read`, `reference_id`, `data jsonb` (carries `mode`/`route` for deep-linking). The dispatcher polls this table and pushes FCM.
- **`device_tokens`** — `token` PK, `user_id`, `platform` (`android|ios|web`). Pruned when FCM reports a token unregistered.

### Tariffs / subscriptions

- **`subscription_plans`** — `code` UNIQUE (`free|basic|pro|enterprise`; plus `trial` from 0020), `name`, `price_monthly`, `max_products`, `max_images_per_product`, `commission_rate`, `credit_limit` (0027), `features_uz`/`features_ru` (jsonb), `is_recommended`. Seeded in 0013.
- **`subscriptions`** — active/pending plan per seller (`plan_code`, `billing_period`, `status`, `started_at`, `expires_at`).
- **`subscription_history`** — audit of plan moves (`from_plan_id`/`to_plan_id`, `reason`); written by `admin_set_shop_plan()`, the single choke point that also copies the plan's `credit_limit` onto the seller.
- **`subscription_receipts`** — payment-screenshot moderation flow: `plan_code`, `billing_period`, `amount`, `payment_screenshot_path`, `status` (`none|pending|approved|rejected|cancelled`), approve/reject/expiry timestamps, `rejection_reason`.
- Product/image quota enforcement is gated by `is_tariff_enabled()` (an `app_settings` flag) via `BEFORE INSERT` triggers on `products`.

### Wallet / ledger (migration 0027)

- **`wallet_transactions`** — append-only signed so'm ledger: `seller_id`, `amount` (signed), `balance_after` (denormalised running balance), `type` (`commission|topup|adjustment|refund`), `order_id`, `note`, `created_by`. Separate from subscription receipts (no plan/period). Soft-freeze ladder: balance below `-credit_limit` opens a 48h grace window, then the sweeper flips `is_suspended_due_to_debt`.

### Shop services & app settings

- **`shop_services`** — PK `(shop_id, service_type)`: per-service config (`enabled`, `min_order_amount`, `fee_amount`, `warranty_months`, `installment_months`).
- **`app_settings`** — `key` PK, `value jsonb`. Holds the `tariff_enabled` master switch and the **receiving card** (`receiving_card` key → `{card_number (16 digits), card_holder, bank_name}`), used by sellers to know where to send tariff/top-up payments. Admin manages it under `/admin/settings/receiving-card`; sellers read it via `/seller/tariff/...`.
- **`news`** / **`banners`** — marketing content: news (title/body/data jsonb, `published_at`, `is_active`) and home banners (`image_url`, `action_type`/`action_value`, `sort_order`, `is_active`).

### AR models

AR state lives directly on `products` (`ar_status`, `ar_video_url`, `ar_model_url`, `ar_rejection_reason`, `ar_meshy_task_id`, `ar_error_reason`) — there is no separate `ar_models` table. The lifecycle is `none → processing → pending_review (admin QC) → approved | rejected`. Generated `.glb` files are re-hosted in the `product-ar-models` R2 bucket.

## 6. API Contracts

### Base URL & versioning

- Production base: **`https://api.woody.uz`**. Every router is mounted under the **`/api/v1`** prefix (`app.include_router(api_router, prefix="/api/v1")`).
- OpenAPI/docs: `/api/v1/openapi.json`, `/api/v1/docs`, `/api/v1/redoc`.
- All handlers are `async def`.

### Authentication

- Scheme: **own JWT, HS256** (PyJWT). Clients send `Authorization: Bearer <access_token>` on every protected request. No external auth provider.
- Token payload: `{sub, phone, role, permissions, token_type, jti, iat, exp, iss, aud}`. `iss`/`aud` are verified on decode; `token_type` separates **access** vs **refresh** (an access token replayed at `/auth/refresh` is rejected).
- Login is phone + OTP (Eskiz SMS), not password:
  - `POST /api/v1/auth/otp/request` `{phone}` → `{sent, cooldown_seconds}`. Rate-limited.
  - `POST /api/v1/auth/otp/verify` `{phone, code}` → `TokenPair` `{access_token, refresh_token, token_type:"bearer", expires_in}`.
  - `POST /api/v1/auth/refresh` `{refresh_token}` → new `TokenPair`.
  - `POST /api/v1/auth/logout` `{refresh_token}` → 204.
- **Effective role is recomputed per request** (`get_effective_role`), never trusted from the JWT claim. Roles: `super_admin` (only the `SUPER_ADMIN_PHONE`) and `manager` (with optional delegable moderator scopes). Guards: public (none), `require_user` (any signed-in mobile user → 401), `require_admin` (any admin + path-derived scope check → 401/403), `require_role("super_admin")` (specific role).
- `GET /api/v1/me` is the source of truth for the resolved role + fresh permissions; `PATCH /me`, `DELETE /me` manage the profile.

### Standard request headers

- `Authorization: Bearer <token>` on every protected endpoint.
- **`Accept-Language`** — drives dynamic-content localization. Resolved by `parse_accept_language` to one of **`uz | ru | en`** (default/fallback `uz`). Accepts both the bare code the Flutter app sends (`ru`) and full browser-style values (`ru-RU,ru;q=0.9,en-US;q=0.8`), picking the highest-q supported subtag. Used to localize catalog category/attribute labels, cancellation reasons, OTP SMS template selection, etc. An unsupported header never 4xxs — it silently falls back to `uz`.
- `Content-Type: application/json` for JSON bodies.

### Route namespaces

- **Unauthenticated:** `GET /health`, `GET /health/ready`; `/auth/*`; `/openapi.json`, `/docs`; **`POST /webhooks/payme`** (Payme Merchant JSON-RPC, HTTP Basic — not JWT).
- **`/catalog/*`** (public storefront read): `/catalog/banners`, `/catalog/categories`, `/catalog/attributes`, `/catalog/products` (filtered list), `/catalog/products/{id}`, `/catalog/products/{id}/similar`, `/catalog/shops/{shop_id}`, `/catalog/news`, `/catalog/settings/{key}` (includes `payment_methods` for Payme/Click visibility).
- **Customer (signed-in, no explicit prefix on the router):** `/cart/items` (GET/POST/PATCH/DELETE), `/cart` (DELETE), `/favorites` (GET/POST/DELETE), `/orders` (list), `/orders/cancel-reasons`, `/orders/{id}`, `/orders/quote`, `POST /orders`, `/orders/{id}/cancel`, **`POST /orders/{id}/pay/{payme|click}`** (mint checkout URL once `awaiting_payment`), `/reviews` (GET/POST), `/push/device-tokens`.
- **`/chat`-area (signed-in):** `/chats`, `/chats/{id}/messages`, `/chats/{id}/read`, plus the user notification inbox `/notifications`, `/notifications/{id}/read`, `/notifications/read-all`.
- **`/seller/*`** (seller bearer, shop-scoped): `/seller/me`, `/seller/shop`, `/seller/products` (CRUD + `/archive`, `/restore`, `/{id}/ar-scan/photos`, `/ai-suggest`), `/seller/orders` (+ `/{id}/status`, `/{id}/delivery-fee`, `/{id}/accept`), `/seller/dashboard`, `/seller/achievements`, `/seller/leaderboard`, `/seller/analytics`, `/seller/reviews`, `/seller/tariff/*` (plans, current, receipts, history, **`/pay`**, receipt status), `/seller/wallet` (+ `/transactions`, `/topups`, **`/deposit`**), `/seller/ar-tokens/*` (**`/buy`**, purchase status), `/seller/services`, `/seller/attributes`, `/seller/verification/documents`.
- **`/storage/*`** — user-facing presigned upload helpers; **`/admin/storage/*`** — admin presigned PUT/GET (R2).
- **`/admin/*`** (admin panel; each area is also a moderator scope): `/admin/orders`, `/admin/products`, `/admin/sellers`, `/admin/shops`, `/admin/customers`, `/admin/categories`, `/admin/reviews`, `/admin/tariffs`, `/admin/wallets`, `/admin/banners`, `/admin/news`, `/admin/notifications`, `/admin/analytics`, `/admin/dashboard`, `/admin/achievements`. **Owner-only (never delegable):** `/admin/settings` and `/admin/managers`.
- **`/realtime/*`** + WebSocket endpoints for live chat/notification updates; **`/internal/ar-webhook`** is the alternate AR-completion callback.

### Pagination conventions

- **Offset/limit** is the norm (no opaque cursors). List endpoints take `limit: int = Query(..., ge=1, le=<max>)` and `offset: int = Query(0, ge=0)`. Defaults vary by surface — e.g. catalog products default `limit=15` (max 200), customer orders default `limit=20` (max 100), similar products default `limit=10` (max 50). The rule card baseline is `limit=20, le=100`.
- List responses that need it return a wrapper with a `total` count alongside the rows (e.g. `CatalogProductList {items, total}`, `CustomerOrderList {items, total}`); the client paginates by advancing `offset`. Simpler lists return a bare array.
- Catalog product filtering is rich: `category_id`, `subcategory_id`, `shop_id`, `color[]`, `min_price`/`max_price`, `in_stock`, `has_delivery`, `discounted`, `search`, `sort` (e.g. `newest`).

### Error response shape

- Errors use FastAPI's default JSON body: **`{"detail": "<code-or-message>"}`**. Domain services raise typed exceptions that routers translate via a `_translate(exc)` helper to stable string codes:
  - `422 invalid_phone`, `429 rate_limited` (with **`Retry-After`** header), `410 otp_expired`, `429 otp_attempts_exhausted`, `401 invalid_code`, `401 invalid_refresh_token`, `403 account_blocked`.
  - Auth/permission gates: `401 not_authenticated`, `403 insufficient_role`, `403 insufficient_permission`.
- Validation failures (pydantic) return FastAPI's standard `422` with a `detail` array of field errors.
- Non-domain failures (DB down, R2 5xx) are not wrapped — they propagate to FastAPI's default `500` handler.

### Architectural anti-patterns (cross-cutting themes)

- **SSR auth side-effects (AUTH-01).** Mutating cookies during a React Server Component render is structurally fragile in the App Router; refresh belongs in middleware / route handlers / server actions. This is the single highest-leverage structural fix.
- **Eager / duplicated data fetching (DATA-01, DATA-02).** Same heavy aggregation fetched twice; presigning every row regardless of use. Adopt `cache()` + lazy/on-demand fetching as a repo convention.
- **Unbounded list rendering (UX-01).** No pagination on admin lists is a correctness bug at scale, not just UX — the backend already supports offset/limit, so this is purely a frontend gap.
- **Incomplete refactors shipped (FE-01).** A color-palette migration was merged half-done. Add CI guards (grep for removed token names) so a partial refactor fails the build.
- **Type system used for shape, not content (FE-05, and the Flutter dual-hash / enum mirrors).** Several cross-surface contracts (trilingual dictionaries, status enums, the OTP signature hash, RBAC scope lists) are hand-mirrored across repos and only shape-checked. These need parity tests, not just types.
- **Best-effort sequential loops (CART-01).** Guest-cart merge awaits per item and swallows failures; prefer batch endpoints + explicit partial-failure reporting.

## 8. Technical Roadmap (6–12 months)

A pragmatic, phased plan. Phase 0 is the debt above; Phases 1–3 scale the platform toward enterprise-grade.

### Phase 0 — Stabilize (weeks 0–4)

- Land the **3 High** debt items (AUTH-01 silent-logout, FE-01 broken styles, FE-02 iOS deep-link placeholder) and the **6 Medium** items.
- Flip pending go-lives that are code-complete but config-gated (per repo memory/notes): **FCM iOS APNs**, **Eskiz template approvals** (all 3 locales matching the signing-key hash), **AR Meshy key + `AR_PIPELINE_ENABLED`**, **AI deployment**, and **admin CSP enforce**.
- Reconcile the **deploy-doc drift** (systemd vs Docker for backend/admin) so the runbook matches reality.

### Phase 1 — Scalability & Performance (months 1–3)

- **Caching layer.** Introduce Redis (already an optional dependency) as a read cache for the hot public catalog paths (`/catalog/products`, categories, attributes, banners) with short TTL + tag invalidation on writes. The catalog is read-dominant and the biggest scaling lever.
- **Database.** Audit indexes against the live slow-query log (the audit confirmed good coverage on current hot paths; validate under real traffic). Add **cursor (keyset) pagination** for the largest tables (orders, products, wallet_transactions) — offset/limit degrades on deep pages. Plan a **read replica** + pooler (PgBouncer) before the single primary saturates; right-size the asyncpg pool per worker.
- **Backend throughput.** Confirm uvicorn worker count vs CPU; ensure no remaining sync I/O on the event loop (BE-04 streaming fix folds in here). Add request-level timeouts/circuit-breakers around Eskiz/Meshy/Azure so a slow provider can't exhaust workers.
- **Flutter performance.** Enable and validate **Impeller** (default on recent Flutter for iOS; verify Android), profile jank on the home feed and chat lists, audit `const`/keys on long lists, and confirm `cached_network_image` eviction policy. Ship image **AVIF/WebP** from the pipeline (also FE-07).

### Phase 2 — DevOps & CI/CD (months 2–5, parallel)

- **Single source-controlled workspace.** The root and `docs/` are **not** under version control today (each repo is a separate git repo; root `TZ.md` itself isn't tracked). Establish a top-level repo (or git submodules / a monorepo tool) so platform-level docs and cross-repo contracts are versioned and reviewable.
- **Test gates in CI.** Make every deploy pipeline **block on tests** — backend `pytest` (726+ passing), Flutter `flutter test` (221+) + `dart analyze`, admin/frontend `tsc --noEmit` + `eslint` + `next build`. Add the cross-repo **enum/RBAC/OTP-hash parity** checks as a dedicated CI job (these are hand-mirrored and the most likely silent drift).
- **Containerize uniformly.** Backend and admin to Docker (frontend already is) for reproducible deploys; pin base images; add health-check probes. Remove git-tracked tooling waste (`.claude-flow/`, `.swarm/`, `ruvector.db`, build caches) across repos.
- **Observability.** Add backend error tracking (Sentry was deliberately removed from Flutter to avoid the `FlutterError.onError` clash — choose a backend-side sink), structured JSON logging with request IDs, and basic metrics/tracing (OpenTelemetry) on the FastAPI app. Mobile already has Crashlytics + Analytics.
- **Migrations discipline.** Keep the `woody migrate` discrete CI step; assert head consistency (the docs note drift between `0027` in system_design and `0035/0036` in code — pin the true head).

### Phase 3 — Feature Maturity / Enterprise-grade (months 4–12)

- **Click settlement webhook.** Payme Merchant API is **live** (orders, tariffs, AR tokens, wallet deposits + fiscalization; strict `awaiting_payment` gate; refund cancels the order). Click today only mints `my.click.uz` URLs — add Prepare/Complete (or equivalent) merchant callbacks so Click payments auto-confirm the same four targets.
- **Payment UX polish.** Failed/cancelled Payme outcomes in Flutter (`PaymentOutcome` today is only paid/pending/unknown); orders-list Pay CTA; optional payment-return deep link.
- **Realtime chat hardening.** Move from refresh-on-open fallback toward fully reliable WebSocket delivery at multi-worker scale (Redis pub/sub fan-out is in place — load-test it); add typing indicators / delivery guarantees.
- **AR pipeline to GA.** Once Meshy is live, add quotas, cost controls, and admin QC SLAs; cache/CDN the `.glb` assets.
- **Search & discovery.** Postgres full-text or a dedicated search service for the catalog as the product count grows; recommendation tuning (the feed already supports discount/popular/recommended sorts).
- **Trust & safety / ops tooling.** Admin audit log, bulk moderation, seller analytics depth, dispute/refund flows tied to the wallet ledger.
- **Internationalization at scale.** Move the hand-synced trilingual dictionaries (FE-05) and DB content translations toward a managed translation workflow with parity enforcement.

### Conventions

- **Money** is integer so'm throughout. **Timestamps** are `TIMESTAMPTZ`. Status columns are `text` + `CHECK`, never DB enums.
- **`Accept-Language`** (`uz`/`ru`/`en`, default `uz`) drives all dynamic-content localization; an unsupported value silently falls back, never 4xxs.
- **Auth** is phone + OTP → own HS256 JWT (access + refresh); the effective role is recomputed every request, never trusted from the JWT claim.
